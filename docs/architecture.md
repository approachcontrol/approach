# Architecture

`approach` is a Go Bubble Tea TUI for managing git worktrees across repositories. User-facing behavior and key bindings are documented in `docs/tui-guide.md` (`README.md` is the short overview); session hooks and storage are `docs/agent-sessions.md`; config reference is `docs/config.md`; Flow phase semantics are `docs/flow-phases.md`; the read-only GraphQL API is `docs/graphql-api.md`.

An interactive isometric package map — buildings for packages, cables for control/data/mutation paths, legend and file citations — lives in [`docs/system-map.html`](system-map.html).

## Package Map

- `cmd/approach/` — entrypoint. Handles `--version`, `session-hook --provider claude|codex|cursor`, the `plan save|list|read|status set|phase set` and `flow create|list|read|phase complete|phase block|phase needs-attention|phase restart|phase reset|phase set|phase add-child|phase agent set|plan save|plan set|issue set|pr set|merge set` subcommands (`plan.go`, `flow.go`), database inspection and migration (`db.go`), and `serve` (`serve.go`), which hosts the read-only GraphQL API. Subcommands resolve the artifact root without starting the TUI; only `serve` scans repos, and it does so per request. `flow create --prepare-worktree` reuses the model's preparation lifecycle without launching an agent.
- `config/` — optional TOML from `$XDG_CONFIG_HOME/approach/config.toml` or `~/.config/approach/config.toml`. Missing config is non-fatal; unreadable files, malformed TOML, wrong types for known keys, and invalid known values are startup-fatal, while unknown sections/keys are ignored for version compatibility.
- Auto-merge shares the view-independent Flow poll and tracked phase-launch lifecycle, but not AutoMode's completion-edge drain. The poll level-triggers ready semantic merge phases, resolves the nullable per-Flow override against default-off `[flow].auto_merge`, and passes the policy to the store's final launch-ID guard. These launches remain headless and reuse the existing preparation, dependency, lease, attempt, terminal, and session fences.
- `scanner/` — discovers repos under `WORKTREE_ROOT`, `[scan].root`, or `~/dev` (default depth 2, reducible via `[scan].max_depth`), excluding `*-worktrees`.
- `gitquery/` — read-only git queries. `parse.go` is pure parsing; `runner.go` defines the `Runner` seam wrapped by a `Querier` (`NewQuerier` injects a fake `Runner` for tests).
- `beadsquery/` — read-only Beads queries. Its injected `Runner` is the query process-launch seam and owns `bd -C <absolute repo>`, the selected working directory, environment isolation, and bounded output. Ready delegates dependency-graph computation to `bd ready`; Blocked/Open/In-Progress use read-only uncapped status queries, while Closed bounds `bd list -s closed` to the newest 100 and independently reads the aggregate total from `bd stats --json --no-activity --readonly`. `Show` returns the raw human-readable output of `bd show <id> --readonly` without parsing or trimming. Pure captured-JSON parsers enforce required display fields; the stats parser accepts direct `summary.closed_issues` and the v1 envelope while rejecting missing, null, fractional, negative, wrong-type, or overflowing totals. Ready/Blocked/Open/In-Progress sort by priority then natural ID, while Closed requires RFC3339 `closed_at` and sorts newest-first with deterministic ID ties. The package marks only a missing executable or exact no-project/no-database diagnostics with `ErrNotConfigured`; the classification wrapper preserves the original runner cause, while all other runner and parser failures retain useful error detail.
- `beadsmutate/` — the sole sanctioned Beads write adapter. Its only operation is `bd update --claim -- <trimmed-id>` against a cleaned absolute repository path, through its own injected `Runner`; the positional separator keeps flag-shaped IDs from being interpreted as options. The executable runner uses both `bd -C <repo>` and that repository as its process directory, strips ambient database/repository selectors while retaining the query runner's output/telemetry/auth allowlist plus `BEADS_ACTOR`, bounds stdout and stderr, and preserves process-error causes. `beadsquery` remains strictly read-only.
- `actions/` — git mutations (worktree create/remove/prune/unlock, branch delete, stash drop, fetch `--prune`, pull `--ff-only`), clipboard, VS Code, editor commands, tmux/Zellij/terminal launches, and Codex/Claude/Cursor launch/resume command construction with Approach hook metadata. `actions.FlowLaunchRoleOf` is the inverse classifier at this adapter boundary. The tracked tmux and embedded-prompt consumers recover a Flow launch role from the finished context and validate the role-shaped metadata they accept; saved-session resume validates its known role directly. Lifecycle policy stays in `model/`. `tmux_mode.go` adds the tmux-mode transport: per-repo session naming (`RepoAgentSessionName`), the create-or-reuse window builder (`RepoTmuxAgentLaunch`) on the user's *default* tmux server, and the availability/attach helpers. Ordinary routes reuse the same self-deleting launch script as every other transport. A tracked Flow phase wraps that script with the pinned Approach executable — falling back to the running binary only when the launch is unpinned — and the private lease handshake, preserving cwd, `APPROACH_*` exports, hook wiring, and original agent argv.
- `internal/launchcontrol/` — controller-owned, crash-recoverable Flow phase results. One package holds the verb table (every `flow` CLI leaf is proxied+replayable, proxied+non-replayable, or direct), the shared `Execute` every proxied verb runs through, the per-launch durable log under `<artifact-root>/launches/<launch-id>/`, the per-state-root Unix socket the TUI serves, replay under the latest-launch gate, exit-evidence reconciliation, and 14-day retention. Import rules are asserted by a test: it imports `flowstore`, `internal/artifacts`, `internal/flowlease` and nothing else in the module; liveness enters as an injected probe, exit evidence as a value, and the applied notifier as a callback, so `sessions`, `model`, and `cmd/approach` depend on it without a cycle.
- `internal/flowlease/` — secure Flow-scoped advisory leases and the private tmux spawn/runner protocol. Stable lock files live under `<artifact-root>/flow-leases`; nonce-bound single-use handoffs live under `<artifact-root>/flow-launch-handoffs`. The runner owns a close-on-exec `flock`, gives the supervised agent process group foreground ownership of the pane PTY, and releases Flow ownership only after the agent or its canceled process group exits. An immutable `runner-claim` selects one runner before lease acquisition; the parent then holds the store reservation through `ready` → `decision=commit` → `started` → `started-confirmed`, consumes an identity-bound bounded `failure` record when the claimed runner's setup or start fails, and uses exact-component tmux cancellation for bounded failures.
- `agent/` — supported agent command names (`codex`, `claude`, `cursor-agent`) with normalization and validation, persisted-command compatibility normalization, and `Resolve`, which reduces the stored per-provider model and reasoning-effort preferences to the single selection that applies to one command.
- `sessions/` — agent-session metadata and normalized transcripts under the user state dir; ingests Claude/Codex/Cursor hook payloads. Blank or whitespace-only session IDs are rejected at ingest and in the store; session dirs are keyed by a hash of the raw provider session ID. `Store.Read(provider, sessionID)` uses that exact key and verifies the decoded metadata carries the same provider and byte-exact ID. `IsActive(status, endedAt)` is the single liveness rule shared by stored records and Flow session mirrors: a nonblank status is active unless it is `ended`, while legacy blank-status records are active only when `EndedAt` is zero.
- `embeddedterm/` — runtime-only PTY process management for embedded CLI agents (sessions-mode resumes plus flows-mode phase and repair launches, both headless and interactive). It owns PTY start, output capture, live visible lines, input forwarding, resize, lifecycle state, and termination behind a small API so model tests can fake terminals. `StartCommandWithOptions` accepts an optional `OutputTransform` that rewrites child output before the emulator (used to render claude and cursor-agent stream-json).
- `claudestream/` — renders the `claude --print --output-format stream-json --include-partial-messages` JSONL event stream into readable terminal lines (init header, thinking/tool-call/tool-result/text blocks streamed token-by-token, closing summary). It is a stateful, streaming `embeddedterm.OutputTransform` that renders from `stream_event` deltas and suppresses the duplicate aggregated `assistant` events (falling back to them if no deltas appear); non-JSON lines pass through verbatim so provider errors stay visible.
- `cursorstream/` — renders the `cursor-agent -p --output-format stream-json --stream-partial-output` JSONL event stream into readable terminal lines (init header, assistant text, tool calls, result). Non-JSON lines pass through verbatim so provider errors stay visible.
- `planstore/` — saved plans at `<root>/plans/<plan-id>/` (`meta.json` + `plan.md`).
- `flowstore/` — task-centric Flow records and per-epic progression rows in `<root>/approach.db`. The pure-Go SQLite backend uses WAL, a per-connection busy timeout, indexed projections for repository/status/time queries, and `BEGIN IMMEDIATE` writer serialization. Schema v3 adds `flows.prepared_at`, the protected receipt trigger, and `epic_progressions(repo_path, epic_id, enabled, updated_at, record)`. Schema v4 retains that layout while requiring `done` in progression JSON, fencing legacy inserts/record updates with compatibility triggers. Schema v5 adds a progression-claim marker compatibility trigger. Schema v6 adds the protected `flows.preparation_nonce` generation projection. Schema v7 adds the protected `flows.recovery_generation` projection for recovered-launch state. `Done` is authoritative: active, normal-off, successfully exhausted, and halted are distinct durable states. A preparation-only create returns an opaque one-shot finalizer bound to the created Flow ID and an internal crypto-random generation nonce that general creation cannot supply; it checks that generation before bootstrap, inside the receipt write, and during error reconciliation, so deletion and same-ID replacement cannot transfer the capability. Successful bootstrap is followed by the internal pending-Flow receipt transition, while canceled or failed startup consumes the same capability to block authoritative launchable roots. Normal `Create` and public metadata mutations cannot mint or move the receipt or nonce. Prepared progression enablement revalidates the exact repository/Bead link, receipt, pending status, and open state in the same writer transaction that upserts progression, clearing done and halt. Halting is a separate atomic active-to-halted transition: only authoritative active state may halt, the result is a disabled row carrying a durable child Bead ID/status/message tuple, and an already-halted row is a timestamp-preserving no-op that retains the first cause. Sequential-successor reconciliation takes a successor-specific launch/close reservation that deliberately permits missing and closed records, then runs a separate read-only writer transaction: it reads progression first so inactive—including done—wins, then classifies the exact Flow ID as released, owned obstruction, accepted, or retryable without ever enabling/upserting progression. `NewStore` holds a root-scoped bootstrap lease while it creates or validates the database and, once, canonicalizes legacy `<root>/flows/<flow-id>/meta.json` records through a closed staged database, leaving `<root>/flows/` in place and warning that it is no longer read. After promotion, SQLite is the only Flow/progression read/write authority; plans and sessions remain file-backed. `AllocateID` exposes the canonical timestamped candidate sequence without writing or reserving anything; two allocations can therefore return the same candidate, and exact-ID `CreateWithOptions` remains the atomic collision arbiter. The canonical transition table is `flowstore/transitions.go` (`AllowedNextPhaseStatuses`, `AgentSettablePhaseStatuses`); gating and readiness rules are in `docs/flow-phases.md`. It depends on `agent/` to validate phase agent settings, resolve their field-by-field global fallbacks, and persist settings-only phase edits without readiness or plan side effects.
- `flowownership/` — the single owner of Flow occupancy decisions and the token-fenced ownership lifecycle: reservation, adoption, rejection, handoff, failure retention, and release. It combines in-process attempts, retained slots, leases, Flow and session state, and role-specific probes according to each caller's declared purpose and freshness. Cached occupancy is advisory and may defer work; an authoritative check governs every operation that mutates state or reserves ownership. `flowstore.validateFlowLaunchOccupancy` remains deliberately separate: it is the store-side validation boundary for a phase transition against other running phases, not a caller-side occupancy query.
- `internal/artifacts/` — shared filesystem mechanics: artifact-root resolution, absolute-root checks, `0700` dirs, `0600` atomic writes and lock files, safe IDs, phase-ID normalization (`NormalizePhaseID`), slugging, and the timestamp+slug candidate sequence used by file and SQLite stores. Store-specific schemas, locking, and phase semantics stay in the owning packages.
- `model/` — Bubble Tea state and key handling. Stable pane ownership is `topMode` (Git/Beads), `bottomMode` (Sessions/Plans/Flows), `contentPane`, and the repos/top/bottom focus enum; Active Flows and PR Babysitter are typed full-content takeovers sharing one exact return snapshot. PR Babysitter owns a visible-only, cancellable GitHub-status poll and reuses the ordinary Flow action gates. Startup is fixed at repos focus with Beads/Ready above Flows. Startup, repo changes, and refresh coordinate independent per-mode requests for both stored panes, and current stored-pane results are accepted regardless of focus. Pane-local numbers and arrows mutate only the focused group; Tab/Backspace traverse repos → top → bottom → eligible terminal while raw terminal input retains its keys. Each list remains a value-type `pane.Pane[T]`; modal state remains `modal.Modal`; read-only details page through `actions.PageText` with stale-result protection. Sessions and Flows share one runtime-only embedded-terminal dock and global terminal selection. The selected epic expansion loads children, readiness, and progression independently under one selection identity. Epic toggles, Ready creation, automatic epic advancement, epic halt, and Ready-Bead `S` epic slicing share a kind/token-owned in-Model preparation admission; the slice kind holds it across a whole agent spawn rather than a store round trip, releasing only on its own launch's `LaunchID`-matched result or synchronous launch failure, so a stale result can neither release a newer fence nor report against a different epic. Progression persists a marked receipt-less exact-link Flow identity, holds its launch/close reservation through the post-persistence claim and preparation finalization, and retains the marker on an uncertain claim error. A later retry discovers open marked receipt-less or prepared-pending direct-child Flows before selecting a Ready sibling and repeats the same-actor idempotent claim; consumed `completed`/`merged` markers are ignored so off/on recovery can install a later sibling, while unmarked manual Ready creation remains outside recovery and claim-free. Enablement installs the only startup-independent runtime baseline and prepares its first child without launching it; the view-independent poll compares exact tracked Flow IDs and, on a success-terminal edge, selects the next Ready-order child and submits it to the create-phase launch lifecycle as one create-then-launch intent that also creates, prepares, reconciles, and starts the child's first phase under the advance's preparation admission. Ownership of the created child is installed before the worktree exists and fences the advance edge, never the halt edge. Successor reconciliation runs inside that pipeline, under the reservation it already holds, between the preparation receipt and the first running phase; only acceptance replaces the baseline, and any other outcome blocks the child's startup roots and halts the epic unless progression was already inactive. Confirmed inactive state or reconciled exhaustion removes the baseline, startup never reconstructs it, and a terminal failure of the child's create attempt halts the epic with a `blocked` cause naming that child. The same poll carries a failure-terminal halt edge — `blocked`, `needs_attention`, `closed`, or `abandoned`, with a deliberate close outranking any derived status — that persists the halt through the same preparation admission and then drops the baseline, its minimum-request marker, and any owned successor, so no further child Flow is created; the halted cause reaches the epic expansion through the authoritative progression read. Private create and worktree helpers perform mechanics only; `flowCreator.Create` owns parked creation and preparation, not `FlowStarter.PrepareFlow` or `StartPlan`. Flow launch mutation, ordering, and runtime handoff belong to the Flow launch lifecycle: `requestFlowLaunch` and `handleFlowLaunchEvent` are the sole state-machine boundary. Source handlers retain key ownership, presentation eligibility, and one-shot subprocess checks such as tmux-window liveness, but those checks cannot launch or persist Flow launch state. Selected-Flow headless and auto-mode preferences use locked metadata updates and freshness-guarded cache replacement, while the view-independent AutoMode poll and Flow repair rules remain separate from epic-progression baseline state and pane visibility.
- `model/flow_launch_*.go` — Flow launch orchestration. `flow_launch_intent.go` declares the closed intent kind enum, origin, and route; `flow_launch_adapters.go` builds persistence, exact-session, worktree, bootstrap, occupancy, and launch seams; `flow_launch_context.go` owns the role-specific payloads and `newFlowLaunchContext`; and `flow_launch_lifecycle.go` coordinates reads, preparation, routing, and failure handling. `requestFlowLaunch` and `handleFlowLaunchEvent` are the sole Flow launch state-machine boundary: callers submit typed intent and do not perform Flow launch persistence or runtime handoff. Once the lifecycle resolves that intent into a role payload, `newFlowLaunchContext` selects the role builder and maps each supported variant to one canonical `actions.AgentLaunchContext` plus its route decision. Callers never set Flow marker combinations themselves. Manual phase launch (`g`), AutoMode, tracked phase resume (`r`), all three Flow-associated saved-session resume surfaces, repair (`R`), generic Flow-worktree agent (`s`), PR autofix (`U`), new-Flow Plan Now, and Ready-Bead `F` all cross that boundary. `flow_launch_create.go` coordinates both creation-time starts as source-aware `createPhase` transactions: non-durable allocation, exact create (including the Ready Bead link), canonical startup-root snapshot, worktree and commit resolution, start metadata, bootstrap, launch-ID proof, phase-authoritative agent resolution, and embedded launch, with source-specific presentation fencing and stage-specific recovery. The metadata-before-bootstrap-before-launch-ID order preserves the bootstrap contract: repository hooks can read the authoritative Flow and observe its worktree, branch, and commit before they run, while a start-metadata failure cannot mutate a phase. AutoMode submits an `autoPhase` intent and keeps only completion-edge detection and drain bookkeeping. `TestFlowLaunchContextLiteralsStayInsideTheLaunchModule` in `model/flow_launch_seam_test.go` scans the repository and rejects Flow launch context construction outside the launch module. `TestFlowLaunchLifecycleBackstopStaysWired` keeps the runtime refusal for marker shapes that the syntax scan cannot prove. Flow/session stores retain persistence, prompt helpers retain prompt construction, actions retain process specifications, and terminal packages retain PTY/tmux mechanics; lifecycle adapters call those owners without giving them orchestration policy.
- `model/flow_launch_resume.go` — the `phaseResume` kind. Like AutoMode it dispatches to its own read and prepare stages rather than the lifecycle's new-target-phase preparation rules. The snapshot resolver follows the saved session's provider, requires a worktree, and submits only session identity plus the repo fallback. The authoritative read re-runs resumability against the fresh record, rejects drift, and threads the validated provider and session ID through the tracked write and launch context without re-deriving them. Every resume records a launch ID and runs the normal tmux phase and worktree-agent probes. `previewPhaseResume` withdraws `r` for a retained non-repair Flow terminal; competing launches retain their existing silent refusals.
- `model/flow_launch_generic_agent.go` — the `worktreeAgent` kind behind `s`. It accepts only configured `codex`, `claude`, or `cursor-agent`, requires the exact existing worktree directory, rejects command drift, and uses the then-current model and reasoning effort. It always builds an embedded, interactive, empty-prompt context with no phase, tracked, auto, or repair flags and ignores headless and tmux preferences. Its slot is generic, Flow-scoped, phase-untracked, nondetachable, and retained after process exit until dismissal. No path calls `AddPhaseLaunchID` or `SetPhase`, so captured sessions retain Flow discoverability but cannot attach to phase history.
- `model/flow_launch_saved_session_resume.go` — the `savedSessionResume` kind shared by Sessions-pane `r`, the global dock picker, and inline worktree-session Enter. It validates one exact provider/raw-session-ID key and follows the refreshed record when the cached Flow association changes. An authoritative non-Flow record or a session whose Flow no longer exists delegates to the origin's established route. The final session record supplies the launch context and canonical Flow association. The result is always an interactive embedded saved-resume role with an empty phase ID, no prompt, no launch-ID or phase write, and no tmux or external fallback. Its slot is nondetachable and remains visible after exit until dismissal. Every failure is status-only.
- `model/flow_launch_autofix.go` — the distinct `autofix` kind behind `U`. Its eligibility gate remains `selectedManualMergeFlow` plus a worktree, its prompt is the `[flow_prompts].autofix` template (default `autofix pr #<num>`, editable from `f2`), and persisted headless plus tmux routing still apply. Headless and tmux send the rendered prompt on argv; interactive embedded launches prefill the dock. It is phase-untracked but uses `AgentLaunchContext.FlowAutofix`, not the generic-agent marker. The kind retains its own live-window probes for `U`, `g`, `r`, and `R`. This separation keeps PR gates, prompt delivery, live-window probes, and headless/tmux failure wording out of the generic `s` policy.
- `model/flow_repair.go` — the shared stalled-Flow classifier (`flowRepairObstructionForRecord`), the repair prompt, and the launch-path resolver. It holds no orchestration: the footer predicate delegates to the lifecycle's preview boundary and `R` is submit-only.
- `model/flow_launch_repair.go` — the `repair` kind. Like resume it dispatches to its own read and prepare stages because new-target-phase rules reject exactly the gated phases repair exists for. It permits only embedded `codex`, `claude`, or `cursor-agent`, reuses manual agent settings, and reports role-specific refusals in a fixed order so durable obstacles appear before transient ones. The footer's `R` goes through `previewRepairLaunch`, with the pending-headless-write term added outside the shared preview. The read stage re-runs the stalled-Flow classifier against the fresh record. A live session tied to any phase launch refuses the Flow-scoped repair because the prompt authorizes `phase reset`, `phase set`, and `plan set` across the whole record. Preparation rebuilds the prompt, headless preference, worktree, branch, commit, and plan path from the protected record. It performs no `AddPhaseLaunchID`, and the empty `FlowPhaseID` also prevents `flowLaunchFailureUpdate`, so a failed repair is classified as nothing persisted. Repair reports every failure with a plain status rather than the tracked kinds' `ActionFailedMsg`, which main shows only for the selected repo or an open Active Flows. The install-stage backstop is broader for repair than for other kinds because repair rewrites the whole Flow. The live-session refusal is the one repair rule the footer cannot mirror, so `R` stays advertised and the press reports it.
- `ui/` — stateless Lip Gloss rendering from `RenderParams`. `StackedContentLayout` subtracts terminal-dock rows first, then splits the shared content height with the odd row assigned to the top; each pane must retain six list rows after borders and headers, so budgets below 19 rows degrade to the focused or remembered pane at full height. Top and bottom have separate headers, borders, focus/destructive styling, cursors, filters, status, and empty/error text. Active Flows renders once across the combined content allocation. The full-width embedded-terminal dock remains between the pane row and status bar, with a framed expanded state and one-row collapsed/empty chip.
- `graphqlapi/` — the read-only GraphQL API served by `approach serve`. `source.go` builds one per-request snapshot (one `scanner.Scan` plus one `flowstore.List`) with a single path-normalization rule and a repo↔flow index; `schema.go` holds the schema and thin, lib-agnostic resolvers; `limits.go` is a fragment-aware AST walk enforcing depth, node count, and fragment-cycle limits before execution, plus a snapshot-aware cost bound that multiplies each list field by its real cardinality and charges each scalar its real width — the only thing in front of result amplification over the `Repo.flows` ↔ `Flow.repo` type-graph cycle; `server.go` is the HTTP handler (routing, conditional `Host` allowlist, token auth, body cap, an in-flight semaphore held across snapshot *and* execution, snapshot timeout, sanitized errors, request log). Behavior and the status contract are `docs/graphql-api.md`.
- `web/` — a Next.js (App Router) viewer for the GraphQL API, deployed separately on Vercel with root directory `web/`. No Go code compiles it and it has its own CI job. `make build` and `make fmt-check` ignore it; `make test` reads one file out of it, as below. `web/node_modules` can contain Go files from npm packages, so the go command skips it via `ignore web/node_modules` in `go.mod` (bare `go test ./...` included), while `gofmt` does not read `go.mod` and is filtered by `make fmt-check` instead. All GraphQL access is server-side, so the endpoint and token never reach the browser, and it deliberately never selects `Flow.instructions` or `Phase.notes`. Its GraphQL documents are the one place the schema is duplicated outside Go, so `graphqlapi/web_documents_test.go` extracts them from `web/src/lib/approach-api.ts` and validates them against the real schema — schema drift fails `make test`, not production. Setup, tunnel, and deploy steps are `web/README.md`.
- `internal/version/` — version/commit/date injected via `-ldflags`.

Agent-settings resolution is phase-authoritative for every new target-phase
launch. Manual, automatic, and creation-time launches resolve from the phase row
returned by their launch-ID write; repair resolves the obstructing phase from
the row returned by its reservation, or uses an empty stamp for a graph-wide
obstruction. In both cases the lifecycle snapshots the full per-provider
preference bundle so partial stamps can fall back to the effective provider.
This supersedes the older shorthand above that repair “reuses manual agent
settings.” Session resume, the generic phase-untracked `s` agent, and the
phase-untracked `U` autofix agent retain their source-specific provider rules.

## Invariants (load-bearing — do not break)

- Destructive actions are gated by destructive mode in the model; preserve that safety boundary. Locked worktrees are never deleted or pruned — unlock is a separate action. (See `docs/agent-operations.md` for how this shows up in practice.)
- Plan and Flow phase IDs are normalized (trimmed + lowercased) before matching, so case- or whitespace-variant IDs upsert the same logical phase, and updates collapse duplicate rows left by older records.
- All store roots must be absolute. `WORKTREE_ROOT` overrides `[scan].root`; `TERMINAL` overrides `[terminal].command` for launches outside tmux/Zellij. `[editor].command` is used for plans-pane Markdown editing and falls back to `EDITOR`; provider/launch config fields are parsed foundation only.
- Sessions, plans, and Flows share one artifact root (released-build default `$XDG_STATE_HOME/approach/sessions/v1` or `~/.local/state/approach/sessions/v1`; a development build substitutes `approach-dev`, see below); moving or cleaning it moves saved artifacts too. TUI root precedence is `APPROACH_FLOW_STATE_ROOT` > `APPROACH_PLAN_STATE_ROOT` > `APPROACH_SESSION_STATE_ROOT` > `[sessions].root` > default; CLI subcommands also accept `--state-root` where documented. CLI-launched agents get the resolved root exported.
- Flow writes serialize across the shared SQLite database and honor the existing five-second default lock timeout as SQLite `busy_timeout`; WAL readers remain available while a writer is active. The writer is database-wide rather than per-Flow as it was under the file store, so `SetPhase`/`MarkManualMerge` never hold it across foreign I/O. The bootstrap/cutover lease has its own longer timeout so a large migration cannot make a second process fail. Schema v3 retains the exact Bead-link compatibility trigger and adds an exact receipt trigger that rejects any rewrite of a prepared Flow whose JSON receipt and `prepared_at` projection no longer match, fencing predecessor processes already holding the database open. Schema v4 adds progression insert/update triggers requiring boolean `done`, fencing already-running v3 writers. Schema v5 adds the same protection for the JSON progression-claim marker, fencing already-running v4 writers. Schema v6 adds the nonce projection and trigger for receipt-less preparations, fencing already-running v5 writers. Schema v7 adds a recovery-generation projection and trigger: fresh v6 opens refuse on `user_version`, and a v6 connection already open during migration cannot rewrite a Flow containing reconciliation or recovered-launch state. Versions 0/1 validate the physical v1 predecessor; version 2 validates its exact Flow columns and Bead trigger; version 3 validates its exact full schema, then atomically rewrites progression blobs to `done:false`; version 4 validates the parent-release done-trigger contract; version 5 validates the claim-marker trigger without a nonce projection; version 6 validates the nonce projection and trigger. The v4→v5 step installs only the claim-marker trigger, the v5→v6 step adds the nonce column and trigger, and the v6→v7 step adds the recovery-generation column and trigger. Every supported predecessor reaches v7 while preserving Flow blobs byte-for-byte, and a malformed v3 progression rolls back all rewrites, triggers, and the version stamp. The root directory is the security boundary for SQLite WAL/SHM sidecars.
- One live `flowstore.Store` at a time per process: it owns a pooled SQLite handle, so the TUI opens it once in `cmd/approach` and hands it to the model through `Options.FlowStore` rather than letting a second pool contend for the same writer. CLI subcommands and session hooks open and `Close` theirs per operation; the hook path opens two sequentially (stale-launch resolution, then attachment) and never holds both. The connection pool is capped well above any realistic fan-out rather than tightly: a writer parked in `BEGIN IMMEDIATE` holds its connection for the whole busy timeout, so a small cap lets writers starve the WAL readers that should never block on them, while no cap at all leaks descriptors permanently — SQLite's unix VFS parks fds it cannot close while the process holds POSIX locks on the inode, so idle-closing a pooled connection does not return its descriptor.
- Flow creation refuses a Bead that already has a non-terminal Flow in the same repository, inside the creation transaction. This is an **admission rule, not a state invariant**: the check runs in the same `backend.update` writer transaction that inserts the row (a `List`-then-`Create` pre-check is the racy shape that produced the bug), and it refuses with `flowstore.ErrBeadFlowActive`, wrapped in a `*BeadFlowActiveError` naming the Flow that already holds the slot. A Flow holds its `(repository, Bead)` slot unless `DeriveStatus` reports `closed`, `abandoned`, `merged`, or `completed` — those four release it, so a follow-up Flow for the same Bead is legitimate; everything else, including `blocked` and `needs_attention`, holds it, because those are the states where a human is meant to repair the existing Flow rather than fork a second one. A receipt-less (prepared-but-unfinalized) Flow holds the slot from the moment its record is written, which is the point: the create → finalize window is exactly where the duplicate race lives. The accepted consequence is that a Ready-Bead preparation failure leaves a `blocked` Flow still holding the Bead, and pressing `f`/`F` again names that Flow rather than creating a second one — the user repairs or closes it. Bead IDs are compared trimmed in Go and never matched in SQL, because the `bead_id` column is projected verbatim and legacy migration can land an untrimmed value; `repo_path` is always cleaned on write and so is matched in SQL. A candidate row whose record blob cannot be decoded — an unsupported schema version written by a newer binary, or corruption — is judged by its still-readable `bead_id` projection: one for another Bead stays ignorable, so a single bad row is never a repository-wide outage, but one claiming the requested Bead refuses with `flowstore.ErrBeadFlowUnreadable` naming the row to repair, because its status cannot be derived and admitting it is exactly how the duplicate Flow and duplicate worktree get made. Epic progression's selection pre-filter reuses `flowstore.BeadFlowSlotOccupied` for the same reason: a child the filter selects but the guard refuses is an unbounded create-refuse loop, since the retryable arm sets no backoff. **Known gap:** the guard covers creation only, so `ReopenFlow` and a phase restart can reconstitute a duplicate (create A for bead X → close A → create B for X → reopen A). Extending it to those paths would make unrelated writes start failing whenever a phase update moved a terminal Flow back into an active status, so the store instead tolerates pre-existing duplicates and resolves them deterministically to the most recently updated occupying Flow. Legacy meta.json import (`readAndCanonicalizeLegacy`) bypasses `createWithOptions` and can land duplicates for the same reason. There is deliberately no unique index and no schema version bump: a partial unique index on `(repo_path, bead_id)` would need a migration that fails outright on databases this bug already damaged, and would surface as an opaque constraint error with no way to name the surviving Flow.
- Agents launched by Approach never resolve `approach` from ambient PATH. `internal/controlplane` copies the running binary into `<state-root>/bin/approach-<sha256[:16]>` (0700 directory, 0500 binaries) and launches export `APPROACH_EXECUTABLE`, `APPROACH_BUILD_VERSION`, and `APPROACH_DB_SCHEMA`; the provider session hook is baked from the same pinned path, so the hook and the exported executable can never name different builds. The copy is the point: Homebrew ships `approach` as a cask binary symlinked into `/opt/homebrew/bin`, so a *path* pin would resolve a versioned Caskroom path that `brew upgrade` deletes, and every later launch would be refused. A cached copy cannot be replaced underneath a running TUI, and its name is its digest, so `Pin.Verify` is a re-hash rather than a trust decision. Capture and materialization are two calls for a timing reason: `CaptureSource` hashes the running binary before the repository scan, because `os.Executable` returns a mutable *pathname* and an upgrade landing during that scan would otherwise have the process cache a build that is not the one running — while still labelling it with this process's version and schema. `Materialize` needs the state root and runs later, and re-hashes what it actually copied against the captured digest before publishing or executing it — the window the split exists to survive is the same window in which the path can name a different file, so an upgrade landing inside it is marked `SourceChanged` and startup fails rather than being cached under the old build's name or degraded to an unverifiable source path. The window from process start to the hash remains and cannot be closed portably; it is stated, not hidden. Retention keeps the three most recent copies and never evicts a digest a live launch or a still-running launcher still points at (`<state-root>/bin/pins/<launch-id>` and `launcher-<pid>`), because the hook path is baked into a detached agent's argv and an idle TUI that has not launched yet would otherwise lose its pin when newer builds start against the same root. Every launch kind claims, because every launch kind bakes that argv: the launch claim is written by `applyLaunchStamp`, the single point all of them pass through, and `Materialize` claims the live launcher so retention cannot evict a process that has not launched yet. Launch claims are released by `FinalizeAgentSession`; the launcher claim is released when the TUI exits. A `launcher-<pid>` claim is honoured while that process is alive, even past the 30-day agent-claim expiry, and dropped as soon as it is not — a month-old TUI still owns its pin, and a crashed TUI does not hold a copy forever. The `session-hook` command is a **keep-alive for every provider and never releases**: no provider hook here is a reliable death certificate — Codex wires `Stop`, which fires once per *turn*, and Claude wires `SessionEnd`, which also fires on `/clear` while the agent keeps running — so releasing on one would unpin a live agent still bound to the path baked into its argv. What a hook attests is "this launch was alive just now", so it restamps the claim. Retirement is therefore `FinalizeAgentSession` (which the TUI deliberately skips for detached launches) or expiry 30 days after the last sign of life. The cost is explicit: a detached launch holds its digest for that window, roughly one cached binary per distinct build launched inside it, accepted against evicting a binary a live agent still has to exec. Materialization ends by *executing* the copy (`--version`, with no inherited environment, since it is the one subcommand that opens no root, database, or config): a mode bit is not proof a file can run, and a state root on a `noexec` mount holds a 0500 file `execve` refuses, which every permission check in the package would pass while the only thing the cache exists for fails silently until an agent is already working. If the cache cannot be created, or the copy cannot be run, the pin degrades to the resolved source path with a status notice — this process is executing that path, so it demonstrably runs — and a caching failure never blocks a launch. A launch is refused, without mutating the phase, only when the pinned binary fails verification — and by *every* route that stamps a pin, ahead of its reservation: preflight is not the only path that marks a phase running, and the non-Flow plan, session-resume, and plain repository agents run `approach` commands against the same store. Saved-plan launches verify before the instructions modal opens and again at spawn, so a pin that vanishes while the modal is open cannot start an agent. Claim writes, refreshes, releases, stale-claim cleanup, retention ordering, final pin decisions, and binary unlinks serialize across processes through `<state-root>/bin/.cache.lock`. The owner-only lock refuses a symlink and has a bounded wait. Claim mutations return its named error to their best-effort callers; a contended sweep skips retention and leaves the cache intact rather than failing startup or launch.
- **Phase results are controller-owned.** Every Flow-scoped launch is registered with the TUI's `launchcontrol.Controller` by `applyLaunchStamp` — the single point that also stamps and claims the pin — and receives `APPROACH_CONTROL_ENDPOINT`/`APPROACH_CONTROL_TOKEN`. Proxied `flow` writes travel over the per-root Unix socket, are appended to the launch's log (fsync + dir sync) **before** they are acknowledged, and are applied through the process's one store by the same `Execute` the CLI's direct path uses. The controller saves the exact response under the request ID before releasing the launch lock and marks the sequence applied. If the socket response is lost, the CLI returns that saved success or refusal without appending or applying the request again. A request file without a response remains unfinished; non-replayable operations are indeterminate in that state. Owned live, logged-direct, and replayed mutations carry the registered owner phase into `flowstore`; the store checks recovery revocation and latest-launch ownership in the same transaction as the mutation. Unowned launches omit the owner phase and keep the recovery-only fence. Explicit direct writes to another Flow are not logged or latest-owner fenced. A refused logged request advances the applied high-water mark with `result: refused`, so replay does not retry it. A restarted controller reloads registrations from `launch.json`, replays pending requests exactly once under the same fence and its batch-level latest-launch gate (case 1: the target is already live, mark it; case 2: the phase is where this launch last left it, apply; case 3: it moved, reject the batch and demote only a phase still `running` under this exact launch), and only then listens. Reads never spool. Retention keeps an old launch directory and registration while that launch remains the latest owner of a running phase, even after the normal 14-day limit; an unreadable ownership check also prevents retirement. The sweep demotes only on positive exit evidence — embedded/interactive terminal exit, the lease runner's `exit.json`, or a Claude session record ended more than ten minutes ago for a reason other than `/clear` — and never while the Flow lease is held. A `SessionEnd` hook is not that evidence: Codex `Stop` is per-turn and Claude's `SessionEnd` fires on `/clear`, so the hook only replays (keeping the `reason` on the record) and the same grace covers demotion; Codex and Cursor `ended` records are turn boundaries and never exit evidence at all, and a Claude launch whose latest end is a `clear` is continued, not ended. Plan-review kinds are demoted to `blocked`/`blocked` with the reason leading the notes; every other kind to `needs_attention` with the reason as the outcome; every note ends with the recovery command. Timestamps in the log are diagnostic only: the replay comparator sees a phase's status and owning launch and nothing else, so an unrelated `UpdatedAt` bump can never make a spooled result look stale.
- **Agent instruction surfaces honor the pinned executable; human documentation names the CLI normally.** The unified skill centralizes executable resolution in `references/persistence.md`: a supplied but non-executable `APPROACH_EXECUTABLE` is a persistence failure, never permission to fall back to an ambient build, while an unpinned ad hoc session may use `APPROACH_BIN` or `approach` from `PATH`. Every runnable skill example repeats the self-resolving command word because shell state does not survive between agent tool calls. TUI-generated phase prompts interpolate the pinned path literally and shell-quoted; configured `[flow_prompts]` templates receive the same value through `{approach_bin}`. Prose in `docs/`, `README.md`, and `AGENTS.md` stays bare because it addresses a human shell rather than a Flow-launched agent.
- Development and released state roots are isolated by default. `artifacts.DefaultRoot()` returns `<state>/approach-dev/sessions/v1` for any build whose version is not a published release tag, and `artifacts.ReleaseDefaultRoot()` is what a released build would use. Only the default moves; explicit `--state-root`, `APPROACH_*_STATE_ROOT`, and `[sessions].root` are untouched. The same default backs `sessions`, `planstore`, and `flowstore`, so a development build moves its session history and plan list along with its Flow list — isolated as a unit, which is the point. On top of that, `migrateAuthoritativeDatabase` refuses to advance the schema when *all* of "development build", "stored schema older than this build's", and "canonical root is exactly `ReleaseDefaultRoot()`" hold. `refuseDevLiveCreation` applies the same rule to the path that has no stored schema to compare: `completeCutover` does not migrate, it BUILDS a current-schema database and renames it into place, so a development build importing a legacy `flows/` tree — or bootstrapping an *empty* release default root — reaches the same end state by creating rather than advancing, and is refused too. Both are lifted unless `StoreOptions.AllowDevLiveMigration` is set (`--allow-dev-live-migration` on the TUI; `APPROACH_ALLOW_DEV_LIVE_MIGRATION=1` on the TUI and `approach db migrate`). Role separation narrowed its reach: the acknowledgement still governs *creation* on `approach flow` and `approach serve`, but it no longer lets them migrate a predecessor-schema root, because the role refusal returns first and no environment variable acknowledges that one. The refusal is a typed sentinel, so the cutover-resume path returns it instead of treating the stage as damaged and discarding it, and the "move your database aside" recovery paragraph is never attached to a database that is merely healthy-and-declined. The path condition is exact equality on purpose, and the cost it buys is worth naming: iterating on a schema change means reopening scratch roots the previous iteration of the same development build wrote, and a broader "any root but the dev default" rule would charge a daily acknowledgement toll to protect state no released build reads. **The residual gap:** an explicit shared root — `[sessions].root` on a mixed dev/release team — gets no protection from this guard, unless that root happens to *be* the release default, in which case it does. And even there the guard's scope is a schema *advance*: an already-current release database still opens read-write from a development build without acknowledgement, and the sessions/plans directories are created on the way to that decision. Whether that boundary should tighten to "a development build touches no release-owned state unacknowledged" is still open: role separation now distinguishes read opens from write opens, but the dev-live guard is deliberately a second, independent gate asking "which build" rather than "which role", and it was not widened to cover reads (`approach-5iw`). Isolating dev state by default is what shrinks that exposure to configurations the operator chose deliberately.
- **Only a migrator migrates, and every non-test `flowstore.NewStore` call site names its role.** `StoreOptions.Role` is `RoleMigrator` (TUI startup, `approach db migrate`), `RoleWriter` (mutating `flow` leaves, the hook's session attachment, the TUI's lazy fallback store), or `RoleReader` (`flow list`, `flow read`, `approach serve`, the hook's launch-staleness resolver). The zero value is `RoleMigrator` so the hundred-plus bare `NewStore(StoreOptions{Root: root})` literals in tests keep today's behaviour byte for byte; a `flowstore_test` AST walk over every non-test `.go` file in the module fails the build if a production call site omits `Role`, because grep missed the `model/` caller once. A non-migrator on a predecessor-schema root gets a refusal naming `approach db migrate`, placed ahead of the dev-live guard and returned before `describeUnusableDatabase` can attach "move `approach.db` aside" advice to a database that is merely unmigrated; the refusal is a typed sentinel (`errRoleRefusedMigration`) for exactly that reason. Migration therefore stops being automatic: after a schema bump, `approach flow`, `approach serve`, and the `SessionEnd` hook refuse until `approach db migrate` or a TUI start has run. Creation from empty stays open to every role — but the create path always opens writer-privileged first, because `buildStagedDatabase` and `settleStagedSQLiteFile` both assert `journal_mode=DELETE` and WAL comes only from `openSQLiteBackend`, so a reader would otherwise hold a DELETE-mode database; a `RoleReader` closes that handle and reopens read-only, two opens on the create path and never on the steady-state path. Importing a legacy `flows/` corpus and resuming an interrupted cutover are migrations and are `RoleMigrator`-only, with two distinct refusals, because telling an operator staring at an `approach.db.migrating` that there is a legacy corpus to import is a wrong diagnosis rather than a terse one.
- **A `RoleReader` mutates nothing on the open path, and the checks it drops are replaced rather than deleted.** It resolves its root through `artifacts.ResolveCanonicalRoot` — no `MkdirAll`, no chmod, no `0700` assertion — never runs `discardObsoleteStage`, and skips the database chmod, the `journal_mode=WAL` write, and `secureExistingSidecars`. `SecureCanonicalRoot`'s two chmods *succeed* on a user-owned `0755` or `0500` directory, so a reader that used it would silently repair the very state `db inspect` and `Store.OpenDiagnostics()` exist to report — and `approach serve` would tighten a `0755` root when its root came from `[sessions].root` while merely warning when the same directory arrived via `--state-root`. What `StoreOptions.RootExplicit` varies is only whether a *missing* root is created, never which root helper the role uses. Two things a reader still writes, deliberately: the bootstrap flock (created, chmodded, and stamped with the PID by `AcquireFileLockNoFollow`, so a reader against a genuinely read-only mount fails outright — `Inspect` is the lock-free path), and the `-shm` a `mode=ro` open of a clean WAL database creates. Writes are refused in Go by `sqliteBackend.requireWriter`, called from the `beginTx` closure and from `delete` — a pair, not an enumeration, since every write in the package is either inside a transaction or is `delete`'s single direct `Exec`. The guard sits on the concrete backend rather than in a decorator because `epic_progression.go` reaches past the `backend` interface four times, two of them the reads `approach serve` depends on. `_pragma=query_only(1)` is the SQLite-level backstop underneath.
- **Every real migration writes a verified backup, and every migrated root records its provenance.** `VACUUM INTO <root>/backups/<stem>-v<from>-<timestamp>-<generation>.db` runs in autocommit immediately before `db.Begin` — SQLite rejects `VACUUM` inside a transaction, and anywhere higher in `migrateAuthoritativeDatabase` would make every already-current TUI startup and every refused open pay for a full copy first. The copy is reopened and checked for integrity, for the schema stamp its filename claims, and for its source's row count; retention keeps 8 per migrated file (per-stem, so a staged-file backup can never evict the `approach.db` ones) and prunes only after a successful verify. Peak disk roughly doubles, so an upgrade on a full disk fails at the backup with `user_version` unchanged rather than migrating — `--backup-dir` is the escape hatch and there is deliberately no skip flag. Provenance lives in `<root>/approach.db.meta.json`, never a table: `validateSQLiteSchemaObjects` is exact set equality, so a bookkeeping table would make every database this build touched unreadable by the previous one. `user_version` stays authoritative — a sidecar that disagrees is repaired from it, never the reverse, and never feeds a compatibility decision. Only `RoleMigrator` writes or repairs it, under the bootstrap lease; every other role reports the drift through `OpenDiagnostics.SidecarStale` and changes nothing. Creation writes no sidecar, so a never-migrated root has none and the backup filename falls back to the literal `nogen`.
- **A schema bump cannot ship without declaring what opens it.** `flowstore/schema_manifest.json` is checked in and `//go:embed`ed: one entry per physical schema version, carrying `min_reader_generation`, `min_writer_generation`, `first_compatible_release`, `migration_tested_predecessors`, and release notes. Both a number and a release string, deliberately — the numbers are what `writeSidecar` stamps and what a compatibility refusal compares, and the release string is the only one of the two an operator can act on. `manifest_test.go` is the gate, and it fails on: a `databaseSchemaVersion` with no entry, an entry with an empty release or release notes, a declared predecessor with no executing migration fixture, and a `migration_tested_predecessors` list that is not exactly `supportedPredecessorVersions` — the named slice that replaced the inline chain of `!=` comparisons in `migrateAuthoritativeDatabase` precisely so accepting a new predecessor without declaring and testing it fails the build. Structural invariants (no duplicates, ascending, nothing above this build's version, every `min_*` at or below its own version) are checked too. `db inspect` reports `first_compatible_release`, and a sidecar declaring a floor above this build surfaces on `OpenDiagnostics().Warnings` — a notice and not a refusal, because `user_version` is the authority and the sidecar is a cache that is never believed.
- **The owners lease is what makes a migration refuse rather than race.** `internal/dblease` publishes one file per holder under `<root>/.approach.db.owners/`, each holding an exclusive `flock` on its *own* file for the holder's lifetime — which is why an exclusive lock is the right primitive (there is nothing to share) and why liveness needs no PID heuristic: a dead process released its lock, so a non-blocking exclusive acquire that *succeeds* proves the holder is gone and the file is reaped. The write order is create-locked-then-rename, and both alternatives are wrong: lock-then-write lets a probing migrator read an empty file and report a live holder with no PID and no build, the exact fields the refusal exists to print; write-then-lock lets a probing migrator's acquire succeed on a file whose owner has not locked it yet, conclude the holder is dead, and unlink it, after which the holder locks an unlinked inode and is invisible forever. Scan skips `.tmp-` names for the mirror-image reason — unlinking one would make the holder's `rename` fail `ENOENT`. **Total acquisition order: owners lease, then bootstrap lock, never the reverse**, asserted through a probe seam rather than a comment; the bootstrap lock is held for up to two minutes by a running migration, so taking it first and then refusing would block every other open on a migration that was never going to happen. The scan runs only when a lock-free `user_version` read says the schema would advance, so the ordinary open pays nothing. The TUI takes its lease *before* opening the store and keeps it across the migration, excluding itself by nonce — releasing and reacquiring around the migration would open exactly the window the lease exists to close. `approach serve` takes one on the same order, before its own open, for the same reason; short-lived `flow`/`plan` leaves take none. A holder already at the target schema does not block a migration; `approach db restore` is stricter and refuses while *any* holder is live, because it replaces the file rather than advancing it — and because the leaseless leaves are invisible to the scan, it also asks SQLite directly (`locking_mode=exclusive`, `busy_timeout(0)`; busy means another connection is attached) before it replaces anything.
- **The sidecar records history, migrations validate after they commit, and live handles are fenced.** `sidecarSchemaVersion` is 2, adding an append-only `history` array capped at 100 with a `history_truncated` flag. The bump is safe in one direction only, and only because a build that knows just version 1 fails `validSidecar` on a v2 sidecar, reports it *absent*, and takes `reconcileSidecar`'s `!present` branch, which returns without rewriting — so an older build neither believes nor destroys the newer record. That is pinned by a test restating the predecessor's rule, not assumed. This build still accepts v1: a v1 sidecar is a v2 sidecar with no history, and treating it as absent would drop the `generation_id` that names every backup on disk. A crash between commit and sidecar write is still repaired from `user_version`, now appending a `reconstructed` entry whose `from_version` and `backup_path` are explicitly null rather than guessed. After `tx.Commit()` and before the lease is released, the migration re-validates the schema and round-trips a sample of records through the read path's codec, tolerating records that were already undecodable beforehand; a failure names the backup and the `approach db restore --backup <path>` command that undoes it. Finally, every other check in the package runs at *open*, and a migration by another process can only be observed while a handle is held: a `Store` records `user_version` and the sidecar generation at open, re-reads `user_version` on every write (a same-connection pragma) and the sidecar at most once a second or on `Revalidate()`, and aborts that write and every one after it with `ErrDatabaseGenerationChanged`. Sticky on purpose — a caller that retried could find the throttle window unelapsed and write anyway. Reads are not fenced: a reader that raced a migration gets the partial list the read path already reports.
- **The incident suite is cross-package and runs the real binary.** `internal/regression` is `_test.go` files only. Every mechanism the schema-N controller / schema-(N-1) CLI incident ran through was already unit-tested, and all of those tests passed while it was live, because none of them ran the shipped command line. This package builds `cmd/approach` once per run, extracts the command word from the text `model` actually generates rather than reconstructing it, puts a stub older CLI first on `PATH` under the name `approach`, and asserts a pinned launch completes the phase without ever reaching it. It also pins the unpinned fallback order through a real shell (`APPROACH_EXECUTABLE`, then `APPROACH_BIN`, then `PATH`), a pin surviving its source being replaced, a corrupted pin refusing without moving the phase, the dev-build refusal through the real `db migrate` process, a clean exit with no result landing `needs_attention`, a controller crash between accept and apply applying exactly once (asserted on the applied *sequence*, since a double-apply reaches the same status), and `db inspect` against a newer schema naming the upgrade. It is skipped under `-short`.
- **`flowstore.Inspect` is the diagnostic that never refuses.** It constructs no `Store`, takes no bootstrap lock (that lease is held for up to two minutes by a running migration, and this is the command you reach for while one is running), never opens with `immutable=1` (which would hide uncheckpointed WAL content behind a stale checkpointed view), and never routes through `SecureCanonicalRoot`. Its six tiers are mutually exclusive and total, evaluated in order: `missing` (with the reason keyed on whether a legacy corpus or an interrupted stage is present, and `os.Lstat` so a symlinked `approach.db` cannot slip into the open tier), `open`, `not_writable`, `malformed`, `not_a_database`, `header`. `not_writable` is a disjunction because the two real cases return different codes — a *clean* database in a `0500` directory answers 1544, while a database with a dirty `-wal` and no `-shm` answers 14, since SQLite cannot create the `-shm` it needs to read the WAL; without the second disjunct the post-crash state the command exists to explain would be reported as corruption. Directory writability is probed with `syscall.Access` rather than mode bits, since the mode is not the authority when the process is root or an ACL is in play. `reason` and `next_action` are non-null exactly when `readable` is false; `sidecar_stale` is a comparison and is therefore `null` outside the `open` tier. A database written by a newer build is *reported*, not rejected — the compatibility refusal belongs to the commands that open the store.
- Branch lists hide non-root worktree branches; the root branch stays pinned at the top.
- Transcripts never live inside repositories — keep them under user state with restrictive permissions (see `docs/agent-sessions.md`).
- The GraphQL API is read-only and never exposes transcripts or session metadata. No `Mutation` or `Subscription` root type exists, the handler rejects non-query operations, and phase `sessions`, `launch_ids`, and transcript paths are absent from the schema by construction.
- When a Flow is linked to a saved plan, transitioning a Flow phase to `completed` syncs a matching saved-plan phase with the same normalized phase ID to `completed`; missing plan phases are ignored, and sync failures mark the Flow phase `needs_attention` — except when the post-commit compensation cannot land, because another writer re-completed that phase in the meantime, because a concurrent writer recorded a merge that the demotion would contradict, or because the compensating update could not acquire the writer, in which case the phase stays completed with a stale plan and the returned error is the only signal. Concurrent writes that leave the completion itself alone, such as attaching a session or recording a resume launch, do not suppress the marker. Repeating `completed` for an already-completed Flow phase preserves that completed state even if the linked-plan sync later fails, and re-runs the idempotent plan write.
- Flow repair launches export the Flow ID and shared artifact root with an empty phase ID, never call `AddPhaseLaunchID`, and cannot attach a captured session to phase history. Replayed repair events are silent no-ops. Protected preparation reapplies the current per-Flow `headless` preference, and the `h` toggle refuses while repair or autofix preparation is reading that preference. Generic `s` always launches interactively and ignores the stored preference. Tracked phase launches read headless from the record returned by their own phase write.

## Behavioral Notes

- Flow auto-advance is view-independent: a private unscoped poll detects live completion edges and launches the next AutoMode phase headlessly without changing focus or mode, regardless of the Flow's stored manual-launch preference. It consults `flowownership` without listing tmux sessions or forking a process on the periodic render path; a deferral leaves the drain armed for a later poll. A cleanly exited repair adds a one-shot marker fenced to the first successful unscoped poll generation that began after exit, which can re-arm the same non-merge drain after metadata-only repair or a running-to-ready reset. Retained repairs suppress ordinary completion-edge drains. Non-clean removal records a generation-fenced suppressing outcome until later state first exposes launchable work, so failure, termination, prefill failure, or a detached agent's delayed mutation cannot leak a deferred launch. The latest repair removal outcome wins, allowing a clean retry to replace an earlier failure. The drain picks a candidate and submits an intent; launch orchestration handles the rest. A candidate-phase session defers the automatic launch and re-arms it for session end. A session record that never reaches `ended` therefore stalls that Flow's AutoMode silently. Manual launch names the refusal (`flowLaunchPhaseSessionLiveStatus`) and points to `x` on the selected phase. `handleReleaseSelectedFlowPhaseSession` confirms the release, probes both supported runtime backends, and finalizes each still-live launch through `FinalizeAgentSession`. It refuses phase-wide while any agent is provably live on the phase, and the confirmation calls the remaining sessions unverified because other backends cannot prove liveness. AutoMode itself remains silent, so the footer hint and manual refusal expose the recovery route. Phase resume exempts the session it is reattaching to. A 3 s transient status announces auto-launches, `needs_attention`, and merge-ready transitions unless another status source is active. The auto-launch announcement appears only after the authoritative read and preflight pass. A transition edge outranks both the queued announcement and a launch failure, while messages of equal rank replace each other.
- Launch backend (`[launch].backend`) selects between the embedded terminal (default) and tmux mode. The Flow lifecycle carries tmux as the alternate route (`flowLaunchRouteTmux`, chosen during protected preparation for phase launch and resume intents); non-lifecycle paths branch through `Model.tmuxLaunchRoute` in `model/tmux_mode.go`. Both wrap the single rule in `tmuxLaunchRouteFor`, because the lifecycle holds a snapshot of the backend and probe taken at admission while the Model reads config's live values — two holders of the same decision, not two decisions. Every launch context is built describing its own transport — the non-Flow resume context `sessionResumeLaunchContext` builds is embedded, because the dock is that route's default — and the two transports that are not the dock clear the bit themselves: `actions.RepoTmuxAgentLaunch` for a tmux window and `actions.AgentLaunch` for an external one. Those contexts carry `Embedded = false` — that single bit is what sends `InitialPrompt` to argv instead of an embedded dock prefill that would never arrive, and what leaves the window's own alt screen alone. A phase-tracked tmux route uses the private lease handshake; ordinary tmux windows, repair, autofix, generic Flow agents, and Flow-associated saved-session resumes do not acquire leases. Headless launches, Flow repair, and the plan launch that Flow creation performs never take the tmux route. Both tmux spawn sites also batch a per-repo terminal attempt (`maybeOpenRepoTmuxTerminal`), which opens the shared detached-terminal seam on the session's attach command when `RepoTmuxSessionAttached` sees no client and an in-process pending flag debounces near-simultaneous launches; it is a sibling command that touches no attempt token or reservation, opens nothing inside tmux/Zellij, and degrades to today's attach-command status when no terminal resolves. The lease is Flow-wide successor admission, while the existing live-window probe remains the one-shot guard for reset, repeat resume, repair, and phase session release. Persisted session state cannot substitute for those actions — Claude's hook is `SessionEnd`, while Codex's `Stop` hook records an `ended` session per turn — so they probe tmux directly (`RepoTmuxLaunchWindowLive`) with every relevant launch ID. The probe belongs only on user-initiated choke points and is advisory in one direction; the lease check belongs on render/periodic/admission paths and fails closed. Because the private parent captures bounded stderr, `TerminalLaunchSpec.ErrorDetail` carries handshake and exact-cancellation diagnostics into the launch error a Flow persists as its `needs_attention` note.
- Embedded terminals (sessions-mode resumes and flows-mode CLI launches) are runtime-only and not persisted or restored; quitting while any are running asks for confirmation before terminating them. Keep PTY mechanics in `embeddedterm`; model owns one global slot selection and dock state, unified `ctrl+]` command routing, direct enhanced `ctrl+shift+]` literal-byte routing, `KeyPressMsg` and `PasteMsg` conversion to PTY bytes, picker/confirm state, session/Flow lifecycle metadata, and conversion from saved sessions to `actions.AgentCommand` contexts.
- Keep ordinary Flow phase launch prompts minimal: state the action plus essential location metadata (worktree, branch, commit). Don't embed plan bodies, phase history, or status-update recipes unless the phase can't work without them. Repair prompts are the deliberate exception: they include the obstruction and structured recovery safety rules because the session is untracked and must leave persisted state honest.
