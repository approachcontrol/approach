# Architecture

`approach` is a Go Bubble Tea TUI for managing git worktrees across repositories. User-facing behavior and key bindings are documented in `docs/tui-guide.md` (`README.md` is the short overview); session hooks and storage are `docs/agent-sessions.md`; config reference is `docs/config.md`; Flow phase semantics are `docs/flow-phases.md`; the read-only GraphQL API is `docs/graphql-api.md`.

## Package Map

- `cmd/approach/` — entrypoint. Handles `--version`, `session-hook --provider claude|codex`, the `plan save|list|read|phase set` and `flow create|list|read|phase complete|phase block|phase needs-attention|phase restart|phase reset|phase set|phase add-child|phase agent set|plan set|issue set|pr set|merge set` subcommands (`plan.go`, `flow.go`), and `serve` (`serve.go`), which hosts the read-only GraphQL API. Subcommands resolve the artifact root without starting the TUI; only `serve` scans repos, and it does so per request.
- `config/` — optional TOML from `$XDG_CONFIG_HOME/approach/config.toml` or `~/.config/approach/config.toml`. Missing config is non-fatal; unreadable files, malformed TOML, wrong types for known keys, and invalid known values are startup-fatal, while unknown sections/keys are ignored for version compatibility.
- `scanner/` — discovers repos under `WORKTREE_ROOT`, `[scan].root`, or `~/dev` (default depth 2, reducible via `[scan].max_depth`), excluding `*-worktrees`.
- `gitquery/` — read-only git queries. `parse.go` is pure parsing; `runner.go` defines the `Runner` seam wrapped by a `Querier` (`NewQuerier` injects a fake `Runner` for tests).
- `beadsquery/` — read-only Beads queries. Its injected `Runner` is the sole `bd` process-launch seam and owns `bd -C <absolute repo>`, the selected working directory, environment isolation, and bounded output. Ready delegates dependency-graph computation to `bd ready`; Blocked/Open/In-Progress use read-only uncapped status queries, while Closed bounds `bd list -s closed` to the newest 100 and independently reads the aggregate total from `bd stats --json --no-activity --readonly`. `Show` returns the raw human-readable output of `bd show <id> --readonly` without parsing or trimming. Pure captured-JSON parsers enforce required display fields; the stats parser accepts direct `summary.closed_issues` and the v1 envelope while rejecting missing, null, fractional, negative, wrong-type, or overflowing totals. Ready/Blocked/Open/In-Progress sort by priority then natural ID, while Closed requires RFC3339 `closed_at` and sorts newest-first with deterministic ID ties. The package marks only a missing executable or exact no-project/no-database diagnostics with `ErrNotConfigured`; the classification wrapper preserves the original runner cause, while all other runner and parser failures retain useful error detail.
- `actions/` — git mutations (worktree create/remove/prune/unlock, branch delete, stash drop, fetch `--prune`, pull `--ff-only`), clipboard, VS Code, editor commands, tmux/Zellij/terminal launches, and Codex/Claude launch/resume command construction with Approach hook metadata. `tmux_mode.go` adds the tmux-mode transport: per-repo session naming (`RepoAgentSessionName`), the create-or-reuse window builder (`RepoTmuxAgentLaunch`) on the user's *default* tmux server, and the availability/attach helpers. It reuses the same self-deleting launch script as every other transport, so cwd, `APPROACH_*` exports, and hook wiring are identical.
- `agent/` — supported agent command names (`codex`, `claude`) with normalization and validation, persisted-command compatibility normalization, and `Resolve`, which reduces the stored per-provider model and reasoning-effort preferences to the single selection that applies to one command.
- `sessions/` — agent-session metadata and normalized transcripts under the user state dir; ingests Claude/Codex hook payloads. Blank or whitespace-only session IDs are rejected at ingest and in the store; session dirs are keyed by a hash of the raw provider session ID. `Store.Read(provider, sessionID)` uses that exact key and verifies the decoded metadata carries the same provider and byte-exact ID. `IsActive(status, endedAt)` is the single liveness rule shared by stored records and Flow session mirrors: a nonblank status is active unless it is `ended`, while legacy blank-status records are active only when `EndedAt` is zero.
- `embeddedterm/` — runtime-only PTY process management for embedded CLI agents (sessions-mode resumes plus flows-mode phase and repair launches, both headless and interactive). It owns PTY start, output capture, live visible lines, input forwarding, resize, lifecycle state, and termination behind a small API so model tests can fake terminals. `StartCommandWithOptions` accepts an optional `OutputTransform` that rewrites child output before the emulator (used to render claude stream-json).
- `claudestream/` — renders the `claude --print --output-format stream-json --include-partial-messages` JSONL event stream into readable terminal lines (init header, thinking/tool-call/tool-result/text blocks streamed token-by-token, closing summary). It is a stateful, streaming `embeddedterm.OutputTransform` that renders from `stream_event` deltas and suppresses the duplicate aggregated `assistant` events (falling back to them if no deltas appear); non-JSON lines pass through verbatim so provider errors stay visible.
- `planstore/` — saved plans at `<root>/plans/<plan-id>/` (`meta.json` + `plan.md`).
- `flowstore/` — task-centric Flow records and per-epic progression rows in `<root>/approach.db`. The pure-Go SQLite backend uses WAL, a per-connection busy timeout, indexed projections for repository/status/time queries, and `BEGIN IMMEDIATE` writer serialization. Schema v3 adds `flows.prepared_at`, the protected receipt trigger, and `epic_progressions(repo_path, epic_id, enabled, updated_at, record)`. A preparation-only create returns an opaque one-shot finalizer; successful bootstrap is followed by the internal pending-Flow receipt transition, while normal `Create` and public metadata mutations cannot mint or move the receipt. Prepared progression enablement revalidates the exact repository/Bead link, receipt, pending status, and open state in the same writer transaction that upserts progression. `NewStore` holds a root-scoped bootstrap lease while it creates or validates the database and, once, canonicalizes legacy `<root>/flows/<flow-id>/meta.json` records through a closed staged database, leaving `<root>/flows/` in place and warning that it is no longer read. After promotion, SQLite is the only Flow/progression read/write authority; plans and sessions remain file-backed. `AllocateID` exposes the canonical timestamped candidate sequence without writing or reserving anything; two allocations can therefore return the same candidate, and exact-ID `CreateWithOptions` remains the atomic collision arbiter. The canonical transition table is `flowstore/transitions.go` (`AllowedNextPhaseStatuses`, `AgentSettablePhaseStatuses`); gating and readiness rules are in `docs/flow-phases.md`. It depends on `agent/` to validate phase agent settings, resolve their field-by-field global fallbacks, and persist settings-only phase edits without readiness or plan side effects.
- `internal/artifacts/` — shared filesystem mechanics: artifact-root resolution, absolute-root checks, `0700` dirs, `0600` atomic writes and lock files, safe IDs, phase-ID normalization (`NormalizePhaseID`), slugging, and the timestamp+slug candidate sequence used by file and SQLite stores. Store-specific schemas, locking, and phase semantics stay in the owning packages.
- `model/` — Bubble Tea state and key handling. Stable pane ownership is `topMode` (Git/Beads), `bottomMode` (Sessions/Plans/Flows), `contentPane`, and the repos/top/bottom focus enum; Active Flows is a separate full-content takeover. Startup is fixed at repos focus with Beads/Ready above Flows. Startup, repo changes, and refresh coordinate independent per-mode requests for both stored panes, and current stored-pane results are accepted regardless of focus. Pane-local numbers and arrows mutate only the focused group; Tab/Backspace traverse repos → top → bottom → eligible terminal while raw terminal input retains its keys. Each list remains a value-type `pane.Pane[T]`; modal state remains `modal.Modal`; read-only details page through `actions.PageText` with stale-result protection. Sessions and Flows share one runtime-only embedded-terminal dock and global terminal selection. The selected epic expansion loads children, readiness, and progression independently under one selection identity; epic toggles and Ready creation share durable admission and reconcile progression authoritatively. Private create and worktree helpers perform mechanics only; Flow launch mutation, ordering, and runtime handoff belong to the Flow launch lifecycle. Source handlers retain key ownership, presentation eligibility, and one-shot subprocess checks such as tmux-window liveness, but those checks cannot launch or persist Flow launch state. Selected-Flow headless and auto-mode preferences use locked metadata updates and freshness-guarded cache replacement, while the view-independent AutoMode poll and Flow repair rules remain separate from epic progression and pane visibility.
- `model/flow_launch_*.go` — the Flow launch lifecycle. `flow_launch_intent.go` declares the closed intent kind enum, origin, and route; `flow_launch_attempt.go` owns the exact-ID, token-fenced in-memory reservation; `flow_launch_adapters.go` builds the authoritative persistence, exact-session, worktree, bootstrap, reservation, and launch seams; and `flow_launch_lifecycle.go` owns admission, authoritative reads, preparation, embedded or tmux handoff, failure classification, and release. `requestFlowLaunch` and `handleFlowLaunchEvent` are the sole Flow launch state-machine boundary: callers submit typed intent and do not perform Flow launch persistence or runtime handoff. Manual phase launch (`g`), AutoMode, tracked phase resume (`r`), all three Flow-associated saved-session resume surfaces, repair (`R`), generic Flow-worktree agent (`s`), PR autofix (`U`), new-Flow Plan Now, and Ready-Bead `F` all cross that boundary. `flow_launch_create.go` owns both creation-time starts as source-aware `createPhase` transactions: non-durable allocation, exact-ID admission and session validation, exact create (including the Ready Bead link), tracked launch/close reservation, canonical startup-root snapshot, worktree and commit resolution, start metadata, bootstrap, launch-ID proof, phase-authoritative agent resolution, and embedded handoff, with source-specific presentation fencing between side effects and stage-specific recovery while ownership remains held. The metadata-before-bootstrap-before-launch-ID order preserves the bootstrap contract: repository hooks can read the authoritative Flow and observe its worktree, branch, and commit before they run, while a start-metadata failure cannot mutate a phase. AutoMode keeps only completion-edge detection and drain bookkeeping. Flow/session stores retain persistence, prompt helpers retain prompt construction, actions retain process specifications, and terminal packages retain PTY/tmux mechanics; lifecycle adapters call those owners without giving them orchestration policy.
- `model/flow_launch_resume.go` — the `phaseResume` kind. Like AutoMode it dispatches to its own read and prepare stages rather than the lifecycle's new-target-phase preparation rules. The snapshot resolver follows the saved session's provider, requires a worktree, and submits only session identity plus the repo fallback. The authoritative read re-runs resumability against the fresh record, rejects drift, and threads the validated provider and session ID through the tracked write and launch context without re-deriving them. Every resume records a launch ID, holds the cross-process launch/close reservation through spawn, uses normal Flow occupancy, and runs the normal tmux phase and worktree-agent probes. `previewPhaseResume` withdraws `r` for a retained non-repair Flow terminal; competing lifecycle attempts and repair terminals retain their existing silent refusals.
- `model/flow_launch_generic_agent.go` — the `worktreeAgent` kind behind `s`. Admission trims the selected Flow ID once, reserves that exact ID, accepts only configured `codex` or `claude`, and checks cached occupancy plus the exact existing worktree directory. The first authoritative stage reads that exact Flow and lists sessions for that exact Flow. Preparation rejects command drift, accepts the then-current model and reasoning effort, takes the launch/close reservation, uses its fresh exact record, lists sessions again, and rechecks running phases, live sessions, worktree type, and linked-plan path without reading the plan body. It always builds an embedded, interactive, empty-prompt context with no phase/tracked/auto/repair flags and ignores headless and tmux preferences. The attempt remains the owner until the retained slot is installed; the slot is stamped generic, Flow-scoped, phase-untracked, and nondetachable, and remains occupancy after process exit until dismissal. No path calls `AddPhaseLaunchID` or `SetPhase`, so captured sessions retain Flow discoverability but cannot attach to phase history.
- `model/flow_launch_saved_session_resume.go` — the `savedSessionResume` kind shared by Sessions-pane `r`, the global dock picker, and inline worktree-session Enter. Admission validates one exact provider/raw-session-ID key and indexes it beside the cached Flow reservation, preventing the same session from entering twice while its association is unresolved. The `readingSession` stage calls exact `ReadSession`; its synchronous handler probes the refreshed record's launch window in tmux mode, then either keeps cached A, atomically moves both indexes from A to authoritative B, or releases them before delegating an authoritative non-Flow record to the origin's established route. Only then does `readingFlow` read B and exact-B sessions; a missing B means the saved session outlived its Flow, so the handler releases lifecycle ownership and delegates the refreshed row to the same established route rather than stranding it. Protected preparation takes `ReserveAgentLaunch(B)`, verifies the returned exact open record, re-reads the exact saved-session key, refuses another association move, re-probes that final record's launch window, relists sessions, repeats running-phase and active-session checks, and builds context from that final session record while taking only canonical Flow B from the reserved record. The result is always an interactive embedded saved-resume role with an empty phase ID, no prompt, no launch-ID or phase write, and no tmux/external fallback. The final synchronous backstop refuses every exact-Flow slot, including prefill-pending and exited retained slots. Success appends a nondetachable retained slot, removes both lifecycle indexes in the same Model value, and only then releases the cross-process reservation; exit does not relinquish occupancy, only dismissal does. Every failure is status-only and releases both indexes after its result is handled.
- `model/flow_launch_autofix.go` — the distinct `autofix` kind behind `U`. Its eligibility gate remains `selectedManualMergeFlow` plus a worktree, its prompt remains `autofix pr #<num>`, and persisted headless plus tmux routing still apply. It is phase-untracked but uses `AgentLaunchContext.FlowAutofix`, not the generic-agent marker. Embedded ownership remains a retained slot; tmux ownership remains the in-process `flowAutofixTmuxLaunches` registry probed by `U`, `g`, `r`, and `R`. This separation keeps PR gates, prompt delivery, live-window probes, and headless/tmux failure wording out of the generic `s` policy.
- `model/flow_repair.go` — the shared stalled-Flow classifier (`flowRepairObstructionForRecord`), the repair prompt, and the launch-path resolver. It holds no orchestration: the footer predicate delegates to the lifecycle's preview boundary and `R` is submit-only.
- `model/flow_launch_repair.go` — the `repair` kind. Like resume it dispatches to its own read and prepare stages because new-target-phase rules reject exactly the gated phases repair exists for. Admission permits only embedded `codex` or `claude`, reuses manual agent settings, and names each occupancy refusal in a fixed order — a repair attempt, a phase resume attempt, any other attempt or a retained terminal, a pending headless write — so durable obstacles are reported before transient ones. The footer's `R` goes through `previewRepairLaunch` (`cachedRepairTarget` plus admission occupancy) with the pending-headless-write term added outside it, because admission's occupancy set has no headless notion and is shared with kinds that must not inherit one. The read stage re-runs the classifier against the fresh record, then refuses when a live session in the authoritative session store belongs to any phase launch of the Flow; the effect is Flow-scoped even though the evidence is per phase, because the repair prompt authorizes `phase reset`, `phase set`, and `plan set` across the whole record. The prepare stage takes the repair-specific reservation (`Store.ReserveRepairLaunch`, whose error verb differs from the tracked one and reaches the user), revalidates against the record that reservation returned, and rebuilds prompt, headless preference, worktree, branch, commit, and plan path from it. It performs no `AddPhaseLaunchID`, so the attempt is never marked as having mutated a phase, and a failed repair is classified as nothing-persisted rather than something to correct; the empty `FlowPhaseID` is the second guard, making `flowLaunchFailureUpdate` refuse. Repair also reports every failure with a plain status rather than the tracked kinds' `ActionFailedMsg`, which main shows only for the selected repo or an open Active Flows — a repair refused one asynchronous hop after an explicit key press has to be visible wherever the user has since navigated, which is what the pre-lifecycle path did. The install-stage backstop (`flowLaunchEmbeddedBackstop`) is broader for repair than for the other kinds — it refuses any Flow terminal, not just a repair one — because repair is Flow-scoped and the record it rewrites is the whole Flow. Admission makes that unreachable today; it exists so a future unguarded launch source cannot install beside a repair. The live-session refusal is the one repair rule the footer cannot mirror, since it is decided against the session store in the read stage rather than the display cache, so `R` stays advertised and the press reports it.
- `ui/` — stateless Lip Gloss rendering from `RenderParams`. `StackedContentLayout` subtracts terminal-dock rows first, then splits the shared content height with the odd row assigned to the top; each pane must retain six list rows after borders and headers, so budgets below 19 rows degrade to the focused or remembered pane at full height. Top and bottom have separate headers, borders, focus/destructive styling, cursors, filters, status, and empty/error text. Active Flows renders once across the combined content allocation. The full-width embedded-terminal dock remains between the pane row and status bar, with a framed expanded state and one-row collapsed/empty chip.
- `graphqlapi/` — the read-only GraphQL API served by `approach serve`. `source.go` builds one per-request snapshot (one `scanner.Scan` plus one `flowstore.List`) with a single path-normalization rule and a repo↔flow index; `schema.go` holds the schema and thin, lib-agnostic resolvers; `limits.go` is a fragment-aware AST walk enforcing depth, node count, and fragment-cycle limits before execution, plus a snapshot-aware cost bound that multiplies each list field by its real cardinality and charges each scalar its real width — the only thing in front of result amplification over the `Repo.flows` ↔ `Flow.repo` type-graph cycle; `server.go` is the HTTP handler (routing, conditional `Host` allowlist, token auth, body cap, an in-flight semaphore held across snapshot *and* execution, snapshot timeout, sanitized errors, request log). Behavior and the status contract are `docs/graphql-api.md`.
- `web/` — a Next.js (App Router) viewer for the GraphQL API, deployed separately on Vercel with root directory `web/`. No Go code compiles it and it has its own CI job. `make build` and `make fmt-check` ignore it; `make test` reads one file out of it, as below. `web/node_modules` can contain Go files from npm packages, so the go command skips it via `ignore web/node_modules` in `go.mod` (bare `go test ./...` included), while `gofmt` does not read `go.mod` and is filtered by `make fmt-check` instead. All GraphQL access is server-side, so the endpoint and token never reach the browser, and it deliberately never selects `Flow.instructions` or `Phase.notes`. Its GraphQL documents are the one place the schema is duplicated outside Go, so `graphqlapi/web_documents_test.go` extracts them from `web/src/lib/approach-api.ts` and validates them against the real schema — schema drift fails `make test`, not production. Setup, tunnel, and deploy steps are `web/README.md`.
- `internal/version/` — version/commit/date injected via `-ldflags`.

Agent-settings resolution is phase-authoritative for every new target-phase
launch. Manual, automatic, and creation-time launches resolve from the phase row
returned by their launch-ID write; repair resolves the obstructing phase from
the row returned by its reservation, or uses an empty stamp for a graph-wide
obstruction. In both cases the lifecycle snapshots the full per-provider
preference bundle so partial stamps can fall back to the effective provider.
This supersedes the older shorthand above that repair “reuses manual agent
settings.” Session resume, the generic phase-untracked `s` agent, and the
phase-untracked `U` autofix agent retain their source-specific provider rules.

## Invariants (load-bearing — do not break)

- Destructive actions are gated by destructive mode in the model; preserve that safety boundary. Locked worktrees are never deleted or pruned — unlock is a separate action. (See `docs/agent-operations.md` for how this shows up in practice.)
- Plan and Flow phase IDs are normalized (trimmed + lowercased) before matching, so case- or whitespace-variant IDs upsert the same logical phase, and updates collapse duplicate rows left by older records.
- All store roots must be absolute. `WORKTREE_ROOT` overrides `[scan].root`; `TERMINAL` overrides `[terminal].command` for launches outside tmux/Zellij. `[editor].command` is used for plans-pane Markdown editing and falls back to `EDITOR`; provider/launch config fields are parsed foundation only.
- Sessions, plans, and Flows share one artifact root (default `$XDG_STATE_HOME/approach/sessions/v1` or `~/.local/state/approach/sessions/v1`); moving or cleaning it moves saved artifacts too. TUI root precedence is `APPROACH_FLOW_STATE_ROOT` > `APPROACH_PLAN_STATE_ROOT` > `APPROACH_SESSION_STATE_ROOT` > `[sessions].root` > default; CLI subcommands also accept `--state-root` where documented. CLI-launched agents get the resolved root exported.
- Flow writes serialize across the shared SQLite database and honor the existing five-second default lock timeout as SQLite `busy_timeout`; WAL readers remain available while a writer is active. The writer is database-wide rather than per-Flow as it was under the file store, so `SetPhase`/`MarkManualMerge` never hold it across foreign I/O. The bootstrap/cutover lease has its own longer timeout so a large migration cannot make a second process fail. Schema v3 retains the exact Bead-link compatibility trigger and adds an exact receipt trigger that rejects any rewrite of a prepared Flow whose JSON receipt and `prepared_at` projection no longer match, fencing predecessor processes already holding the database open. Versions 0/1 validate the physical v1 predecessor; version 2 validates its exact Flow columns and Bead trigger. Each upgrades transactionally to v3, preserving every existing Flow blob byte-for-byte. The root directory is the security boundary for SQLite WAL/SHM sidecars.
- One live `flowstore.Store` at a time per process: it owns a pooled SQLite handle, so the TUI opens it once in `cmd/approach` and hands it to the model through `Options.FlowStore` rather than letting a second pool contend for the same writer. CLI subcommands and session hooks open and `Close` theirs per operation; the hook path opens two sequentially (stale-launch resolution, then attachment) and never holds both. The connection pool is capped well above any realistic fan-out rather than tightly: a writer parked in `BEGIN IMMEDIATE` holds its connection for the whole busy timeout, so a small cap lets writers starve the WAL readers that should never block on them, while no cap at all leaks descriptors permanently — SQLite's unix VFS parks fds it cannot close while the process holds POSIX locks on the inode, so idle-closing a pooled connection does not return its descriptor.
- Branch lists hide non-root worktree branches; the root branch stays pinned at the top.
- Transcripts never live inside repositories — keep them under user state with restrictive permissions (see `docs/agent-sessions.md`).
- The GraphQL API is read-only and never exposes transcripts or session metadata. No `Mutation` or `Subscription` root type exists, the handler rejects non-query operations, and phase `sessions`, `launch_ids`, and transcript paths are absent from the schema by construction.
- When a Flow is linked to a saved plan, transitioning a Flow phase to `completed` syncs a matching saved-plan phase with the same normalized phase ID to `completed`; missing plan phases are ignored, and sync failures mark the Flow phase `needs_attention` — except when the post-commit compensation cannot land, because another writer re-completed that phase in the meantime, because a concurrent writer recorded a merge that the demotion would contradict, or because the compensating update could not acquire the writer, in which case the phase stays completed with a stale plan and the returned error is the only signal. Concurrent writes that leave the completion itself alone, such as attaching a session or recording a resume launch, do not suppress the marker. Repeating `completed` for an already-completed Flow phase preserves that completed state even if the linked-plan sync later fails, and re-runs the idempotent plan write.
- Flow repair launches export the Flow ID and shared artifact root with an empty phase ID, never call `AddPhaseLaunchID`, and cannot attach a captured session to phase history. The lifecycle attempt token fences duplicate presses and replayed repair events; a replayed event is a silent no-op. In the prepare stage, `Store.ReserveRepairLaunch` holds an advisory lock shared with `CloseFlow`, reads the authoritative Flow, revalidates eligibility, reapplies the authoritative per-Flow `headless` preference, and releases only after the terminal starts or fails. That lock does not order against `SetHeadless`, which writes under the store's own, so the `h` toggle refuses while a repair or autofix attempt holds the Flow because both re-read authoritative headless state during protected preparation. Generic `s` always launches interactively and ignores the stored preference, so its `worktreeAgent` attempt does not participate in that fence. Tracked phase launches need no such fence because they read headless from the record their own phase write returns. OS process exit releases a stranded lock automatically.
- Exactly one lifecycle attempt owns a Flow launch at a time, and it never lapses. This covers manual, automatic, resume, and repair launches alike; a tracked phase resume takes the attempt at the key press and holds it across its own read and write, and a repair holds one for a whole Flow with no phase named. Saved-session resume additionally owns an exact provider/raw-session-ID index; an authoritative A→B move updates the Flow attempt and session index atomically, and release removes either only for the owning token. An attempt owns its Flow from admission until the embedded slot is installed (the slot then owns it) or until an external handoff's result is consumed; failure persistence re-takes ownership before the slot is dismissed, so the Flow is never unowned while its phase is persisted `running`. Ownership is keyed on the exact canonical Flow ID, released on a token match only, and entered into `failurePersisting` only after `flowLaunchFailureUpdate` confirms there is something to persist — otherwise no persistence message arrives and the Flow would be reserved forever.

## Behavioral Notes

- Flow auto-advance is view-independent: a private unscoped advance poll detects live completion edges and launches the next AutoMode phase headlessly without changing focus or mode, regardless of the Flow's stored manual-launch preference. A cleanly exited repair slot adds a one-shot marker fenced to the first successful unscoped poll generation that began after exit; the marker can re-arm the same non-merge drain after metadata-only repair or a running-to-ready reset. Retained repairs suppress ordinary completion-edge drains, and non-clean removal records a generation-fenced suppressing outcome that remains until a later state first exposes launchable work, so failure, termination, prefill failure, or a detached agent's delayed mutation cannot leak a deferred launch. The latest repair removal outcome is authoritative, allowing a clean retry to replace an earlier failure. Admission, candidate validation, and retry all belong to the launch lifecycle: the drain picks a candidate and submits an intent, and everything after that is the lifecycle's. The lifecycle also lists the Flow's sessions before an automatic launch and refuses while a session on the candidate phase is still live, re-arming so the launch resumes when it ends — which means a session record that never reaches `ended` stalls that Flow's AutoMode silently: repair sees no obstruction while the phase is still launchable, and reset requires `running`. Manual launch refuses on the same occupancy rule but names it (`flowLaunchPhaseSessionLiveStatus`) and points at the route out, which is `x` on the selected phase. Session release is that route: `handleReleaseSelectedFlowPhaseSession` probes both halves through the launch seams, and a confirmation finalizes each still-live launch through the same `FinalizeAgentSession` a clean exit would have run, so no store API and no persisted shape is new. It refuses phase-wide while any agent is provably live on the phase, and the confirmation states that the sessions are unverified, because outside the embedded backend and tmux nothing can prove they are not. AutoMode itself still says nothing — the drain short-circuits on the phase mirror before the read stage, and `handleAutoFlowLaunchRead` may not set a status — so the affordance is the footer hint and the named manual refusal. Phase resume does not join the occupancy list — its check exempts the session it is reattaching to, so `r` still gets a user back into the work — but it is not a cure either: reattaching does not finalize the stale record, and whether the record clears depends on whether the provider reuses its session ID. Because that refusal re-arms, the drain applies the same check to the mirrored sessions the poll snapshot already carries before it submits an intent; otherwise a stalled phase would re-admit and walk the whole session store once a second for as long as it stayed stalled. A 3 s transient status announces auto-launches, `needs_attention`, and merge-ready transitions unless another status from a different source is active; the auto-launch announcement is emitted once the authoritative read and preflight have passed, so a Flow that is refused before it launches announces nothing. It therefore lands a hop after the transition statuses computed by the same poll, which would invert their precedence; the auto-advance source is ranked to absorb that, so a transition edge outranks both the queued announcement and a launch failure while messages of equal rank still replace each other.
- Launch backend (`[launch].backend`) selects between the embedded terminal (default) and tmux mode. The Flow lifecycle carries tmux as the alternate route (`flowLaunchRouteTmux`, chosen during protected preparation for phase launch and resume intents); non-Flow paths branch through `Model.tmuxLaunchRoute` in `model/tmux_mode.go`. Both wrap the single rule in `tmuxLaunchRouteFor`, because the lifecycle holds a snapshot of the backend and probe taken at admission while the Model reads config's live values — two holders of the same decision, not two decisions. Tmux-route contexts carry `Embedded = false` — that single bit is what sends `InitialPrompt` to argv instead of an embedded dock prefill that would never arrive. Tmux launches use external handoff semantics throughout: detached result, no embedded slot, hook-owned completion, and no quit-time cleanup. Headless launches, Flow repair, and both creation-time plan launches never take the tmux route. One consequence is load-bearing: the embedded slot is also the "an agent is live here" fence for phase reset, repeat resume, Flow repair, and phase session release, and a tmux window is not an observable slot. Persisted session state cannot substitute — Claude's hook is `SessionEnd`, so a live window has no session at all, while Codex's `Stop` hook records an `ended` session per turn — so all four actions probe tmux directly (`RepoTmuxLaunchWindowLive`, matching the launch IDs that `repoTmuxWindowName` embeds in window names). The probe is variadic and takes every launch ID the caller owns, because one `list-windows` answers for all of them and an earlier launch's window can outlive a later one that already exited: reset, resume, and release pass the phase's launches, repair passes the whole Flow's, since a repair agent is Flow-wide and a Flow-level obstruction names no phase. Release passing all of them is also what makes its refusal phase-wide, which is the point: a phase can carry a resumed live launch beside a crashed one, and finalizing "every live launch" would record the working agent as ended. Two invariants: the probe belongs only on the one-shot user-initiated choke points (`handleFlowPhaseResetConfirmed`, `handleResumeFlowPhaseSession`, `handleRepairSelectedFlow`, `handleFlowPhaseSessionReleaseConfirmed`) and never in a render-path predicate like `flowPhaseResettable`, `selectedFlowRepairReady`, or `flowPhaseSessionReleasable`, and it is advisory in one direction only — a failed probe reports "no live window" so it can never strand a phase. Do not replace it with a fence keyed on a recorded launch ID: with no release condition, an out-of-band `tmux kill-window` would make the phase permanently unresettable. Because the tmux transport spawns through a wrapper script, its failures would otherwise reduce to the script's exit status; `TerminalLaunchSpec.ErrorDetail` carries the captured stderr into the launch error a Flow persists as its `needs_attention` note.
- Embedded terminals (sessions-mode resumes and flows-mode CLI launches) are runtime-only and not persisted or restored; quitting while any are running asks for confirmation before terminating them. Keep PTY mechanics in `embeddedterm`; model owns one global slot selection and dock state, unified `ctrl+]` command routing, picker/confirm state, session/Flow lifecycle metadata, and conversion from saved sessions to `actions.AgentCommand` contexts.
- Keep ordinary Flow phase launch prompts minimal: state the action plus essential location metadata (worktree, branch, commit). Don't embed plan bodies, phase history, or status-update recipes unless the phase can't work without them. Repair prompts are the deliberate exception: they include the obstruction and structured recovery safety rules because the session is untracked and must leave persisted state honest.
