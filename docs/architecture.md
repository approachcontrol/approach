# Architecture

`approach` is a Go Bubble Tea TUI for managing git worktrees across repositories. User-facing behavior and key bindings are documented in `docs/tui-guide.md` (`README.md` is the short overview); session hooks and storage are `docs/agent-sessions.md`; config reference is `docs/config.md`; Flow phase semantics are `docs/flow-phases.md`; the read-only GraphQL API is `docs/graphql-api.md`.

## Package Map

- `cmd/approach/` — entrypoint. Handles `--version`, `session-hook --provider claude|codex`, the `plan save|list|read|phase set` and `flow create|list|read|phase complete|phase block|phase needs-attention|phase restart|phase reset|phase set|phase add-child|plan set|issue set|pr set|merge set` subcommands (`plan.go`, `flow.go`), and `serve` (`serve.go`), which hosts the read-only GraphQL API. Subcommands resolve the artifact root without starting the TUI; only `serve` scans repos, and it does so per request.
- `config/` — optional TOML from `$XDG_CONFIG_HOME/approach/config.toml` or `~/.config/approach/config.toml`. Missing config is non-fatal; unreadable files, malformed TOML, wrong types for known keys, and invalid known values are startup-fatal, while unknown sections/keys are ignored for version compatibility.
- `scanner/` — discovers repos under `WORKTREE_ROOT`, `[scan].root`, or `~/dev` (default depth 2, reducible via `[scan].max_depth`), excluding `*-worktrees`.
- `gitquery/` — read-only git queries. `parse.go` is pure parsing; `runner.go` defines the `Runner` seam wrapped by a `Querier` (`NewQuerier` injects a fake `Runner` for tests).
- `beadsquery/` — read-only Beads queries. Its injected `Runner` is the sole `bd` process-launch seam and owns `bd -C <absolute repo>`, the selected working directory, environment isolation, and bounded output. Ready delegates dependency-graph computation to `bd ready`; Blocked/Open/In-Progress use read-only uncapped status queries, while Closed bounds `bd list -s closed` to the newest 100 and independently reads the aggregate total from `bd stats --json --no-activity --readonly`. `Show` returns the raw human-readable output of `bd show <id> --readonly` without parsing or trimming. Pure captured-JSON parsers enforce required display fields; the stats parser accepts direct `summary.closed_issues` and the v1 envelope while rejecting missing, null, fractional, negative, wrong-type, or overflowing totals. Ready/Blocked/Open/In-Progress sort by priority then natural ID, while Closed requires RFC3339 `closed_at` and sorts newest-first with deterministic ID ties. The package marks only a missing executable or exact no-project/no-database diagnostics with `ErrNotConfigured`; the classification wrapper preserves the original runner cause, while all other runner and parser failures retain useful error detail.
- `actions/` — git mutations (worktree create/remove/prune/unlock, branch delete, stash drop, fetch `--prune`, pull `--ff-only`), clipboard, VS Code, editor commands, tmux/Zellij/terminal launches, and Codex/Claude launch/resume command construction with Approach hook metadata. `tmux_mode.go` adds the tmux-mode transport: per-repo session naming (`RepoAgentSessionName`), the create-or-reuse window builder (`RepoTmuxAgentLaunch`) on the user's *default* tmux server, and the availability/attach helpers. It reuses the same self-deleting launch script as every other transport, so cwd, `APPROACH_*` exports, and hook wiring are identical.
- `agent/` — supported agent command names (`codex`, `codex-app`, `claude`) with normalization and validation, plus `Resolve`, which reduces the stored per-provider model and reasoning-effort preferences to the single selection that applies to one command.
- `sessions/` — agent-session metadata and normalized transcripts under the user state dir; ingests Claude/Codex hook payloads. Blank or whitespace-only session IDs are rejected at ingest and in the store; session dirs are keyed by a hash of the provider session ID.
- `embeddedterm/` — runtime-only PTY process management for embedded CLI agents (sessions-mode resumes plus flows-mode phase and repair launches, both headless and interactive). It owns PTY start, output capture, live visible lines, input forwarding, resize, lifecycle state, and termination behind a small API so model tests can fake terminals. `StartCommandWithOptions` accepts an optional `OutputTransform` that rewrites child output before the emulator (used to render claude stream-json).
- `claudestream/` — renders the `claude --print --output-format stream-json --include-partial-messages` JSONL event stream into readable terminal lines (init header, thinking/tool-call/tool-result/text blocks streamed token-by-token, closing summary). It is a stateful, streaming `embeddedterm.OutputTransform` that renders from `stream_event` deltas and suppresses the duplicate aggregated `assistant` events (falling back to them if no deltas appear); non-JSON lines pass through verbatim so provider errors stay visible.
- `planstore/` — saved plans at `<root>/plans/<plan-id>/` (`meta.json` + `plan.md`).
- `flowstore/` — task-centric Flow records in `<root>/approach.db`. The pure-Go SQLite backend uses WAL, a per-connection busy timeout, indexed projections for repository/status/time queries, and `BEGIN IMMEDIATE` writer serialization. `NewStore` holds a root-scoped bootstrap lease while it creates or validates the database and, once, canonicalizes legacy `<root>/flows/<flow-id>/meta.json` records through a closed staged database, leaving `<root>/flows/` in place and warning that it is no longer read. After promotion, SQLite is the only Flow read/write authority; plans and sessions remain file-backed. The canonical transition table is `flowstore/transitions.go` (`AllowedNextPhaseStatuses`, `AgentSettablePhaseStatuses`); gating and readiness rules are in `docs/flow-phases.md`. It depends on `agent/` to validate the agent, model, and reasoning effort captured on each phase at creation.
- `internal/artifacts/` — shared filesystem mechanics: artifact-root resolution, absolute-root checks, `0700` dirs, `0600` atomic writes and lock files, safe IDs, phase-ID normalization (`NormalizePhaseID`), slugging, and the timestamp+slug candidate sequence used by file and SQLite stores. Store-specific schemas, locking, and phase semantics stay in the owning packages.
- `model/` — Bubble Tea state and key handling. Stable pane ownership is `topMode` (Git/Beads), `bottomMode` (Sessions/Plans/Flows), `contentPane`, and the repos/top/bottom focus enum; Active Flows is a separate full-content takeover. Startup is fixed at repos focus with Beads/Ready above Flows. Startup, repo changes, and refresh coordinate independent per-mode requests for both stored panes, and current stored-pane results are accepted regardless of focus. Pane-local numbers and arrows mutate only the focused group; Tab/Backspace traverse repos → top → bottom → eligible terminal while raw terminal input retains its keys. Each list remains a value-type `pane.Pane[T]`; modal state remains `modal.Modal`; read-only details page through `actions.PageText` with stale-result protection. Sessions and Flows share one runtime-only embedded-terminal dock and global terminal selection. Flow start orchestration lives behind `FlowStarter`; selected-Flow headless and auto-mode preferences use locked metadata updates and freshness-guarded cache replacement, while the view-independent AutoMode poll and Flow repair rules remain separate from pane visibility.
- `model/flow_launch_*.go` — the Flow launch lifecycle. `flow_launch_intent.go` declares the closed intent kind enum, origin, and route; `flow_launch_attempt.go` owns `flowLaunchAttempt`, the per-Flow launch reservation (copy-on-write, keyed on the exact canonical Flow ID, released on token match only); `flow_launch_adapters.go` builds the authoritative `flowLaunchSeams` (`ReadFlow`, Flow-scoped session list, `AddPhaseLaunchID`, `SetPhase`, plan path/body, launch IDs) in `NewWithOptions`; `flow_launch_lifecycle.go` owns admission, the authoritative read, preparation, embedded/external handoff, failure classification, and release. Callers submit an intent through `requestFlowLaunch` and never decide policy; for manual launch, `previewFlowLaunch` answers the cached footer question with the same admission rules so advertisement and admission cannot disagree. Phase resume has the same guarantee with a deliberately narrower preview (`previewPhaseResume`, below), so the invariant is scoped per kind rather than global. AutoMode admission deliberately skips that cached preview: the advance poll is view-independent and its Flows are frequently absent from the display caches, so launchability is decided entirely by the authoritative read. Manual phase launch (`g` on Flows and Active Flows), AutoMode phase launch, and tracked phase resume (`r`) route through it today; repair and Plan Now still use their legacy launchers. Those sources refuse while a lifecycle attempt holds the Flow (`flowLaunchAttemptOccupied`), and the lifecycle refuses while any signal they publish — an embedded terminal, a pending repair — holds it. AutoMode submits an `autoPhase` intent and keeps only completion-edge detection and drain bookkeeping; the lifecycle owns its admission, fresh read, candidate validation, reservation, routing, failure handling, and release, so manual and automatic launches share one state machine and are mutually exclusive. The two kinds differ in three named places: the candidate resolver (`flowLaunchCandidatePhase`) keeps merge and autoreview-recovery phases manual-only, auto admission refuses silently rather than setting a status, and auto read-stage outcomes (`ok`/`retry`/`stale`/`failed`) decide whether the drain is re-armed or dropped.
- `model/flow_launch_resume.go` — the `phaseResume` kind. Like AutoMode it dispatches to its own read and prepare stages rather than `FlowPhaseLauncher.Preflight`/`Prepare` and the read stage's `flowLaunchCandidatePhase`, whose new-launch rules (prompt rendering, launchable-phase gating, `AddPhaseLaunchID` without `Resume`) reject the `completed` and `skipped` phases resume exists for, and every `needs_attention` one but the autoreview-with-PR-target case manual launch already recovers. The snapshot refusals live here as a `Model` method because resolving `codex` → `codex-app` reads the agent preference; the read stage re-runs the same rules against the fresh record and adds a drift refusal when the phase's latest resumable session is no longer the one the key press named. Session identity — provider, provider session ID, and the resolved agent command — is resolved once and threaded intent → event → context, never re-derived after the write: `AddPhaseLaunchID` appends a launch ID with no session attached, so `LatestPhaseSession` would fall through to a newest-by-timestamp scan and could resume a different session than the read authorized. Both the phase kind the launch reports and its terminal-phase protection come from the record that write returns, with a fallback to the read-stage phase when the record carries none. Occupancy is Flow-scoped like every other kind, and its one spoken refusal is a retained non-repair Flow terminal; a lifecycle attempt, a pending repair, and an open repair terminal refuse silently. `previewPhaseResume` withdraws the footer's `r` for exactly the spoken case, which is why it is narrower than `flowLaunchAdmissionOccupied`. `codex-app` is the standing exception: it stays untracked app navigation with no attempt, no read, and no phase write, so it bypasses occupancy in both admission and the footer, and its fully built launch context rides on the intent because no authoritative read produces one. Every tracked embedded or external launch also holds the store's cross-process launch/close reservation continuously from launch-ID persistence through process or terminal spawn, so a concurrent `CloseFlow` cannot leave phantom launch bookkeeping or start an agent after closure.
- `model/flow_repair.go` — the shared stalled-Flow classifier and isolated repair launcher. Repair permits only embedded `codex` or `claude`, reuses manual agent settings, and deliberately leaves the launch Flow-scoped but phase-untracked; launch/prefill/capacity failures therefore report status without regressing a phase. Its final authoritative read and terminal start run under the store's short cross-process repair/close reservation, so a concurrent close and repair launch have one explicit winner without persisting transient reservation state.
- `ui/` — stateless Lip Gloss rendering from `RenderParams`. `StackedContentLayout` subtracts terminal-dock rows first, then splits the shared content height with the odd row assigned to the top; each pane must retain six list rows after borders and headers, so budgets below 19 rows degrade to the focused or remembered pane at full height. Top and bottom have separate headers, borders, focus/destructive styling, cursors, filters, status, and empty/error text. Active Flows renders once across the combined content allocation. The full-width embedded-terminal dock remains between the pane row and status bar, with a framed expanded state and one-row collapsed/empty chip.
- `graphqlapi/` — the read-only GraphQL API served by `approach serve`. `source.go` builds one per-request snapshot (one `scanner.Scan` plus one `flowstore.List`) with a single path-normalization rule and a repo↔flow index; `schema.go` holds the schema and thin, lib-agnostic resolvers; `limits.go` is a fragment-aware AST walk enforcing depth, node count, and fragment-cycle limits before execution, plus a snapshot-aware cost bound that multiplies each list field by its real cardinality and charges each scalar its real width — the only thing in front of result amplification over the `Repo.flows` ↔ `Flow.repo` type-graph cycle; `server.go` is the HTTP handler (routing, conditional `Host` allowlist, token auth, body cap, an in-flight semaphore held across snapshot *and* execution, snapshot timeout, sanitized errors, request log). Behavior and the status contract are `docs/graphql-api.md`.
- `internal/version/` — version/commit/date injected via `-ldflags`.

## Invariants (load-bearing — do not break)

- Destructive actions are gated by destructive mode in the model; preserve that safety boundary. Locked worktrees are never deleted or pruned — unlock is a separate action. (See `docs/agent-operations.md` for how this shows up in practice.)
- Plan and Flow phase IDs are normalized (trimmed + lowercased) before matching, so case- or whitespace-variant IDs upsert the same logical phase, and updates collapse duplicate rows left by older records.
- All store roots must be absolute. `WORKTREE_ROOT` overrides `[scan].root`; `TERMINAL` overrides `[terminal].command` for launches outside tmux/Zellij. `[editor].command` is used for plans-pane Markdown editing and falls back to `EDITOR`; provider/launch config fields are parsed foundation only.
- Sessions, plans, and Flows share one artifact root (default `$XDG_STATE_HOME/approach/sessions/v1` or `~/.local/state/approach/sessions/v1`); moving or cleaning it moves saved artifacts too. TUI root precedence is `APPROACH_FLOW_STATE_ROOT` > `APPROACH_PLAN_STATE_ROOT` > `APPROACH_SESSION_STATE_ROOT` > `[sessions].root` > default; CLI subcommands also accept `--state-root` where documented. CLI-launched agents get the resolved root exported; `codex-app` receives prompt-only launch metadata plus copyable `--state-root` command examples.
- Flow writes serialize across the shared SQLite database and honor the existing five-second default lock timeout as SQLite `busy_timeout`; WAL readers remain available while a writer is active. The writer is database-wide rather than per-Flow as it was under the file store, so `SetPhase`/`MarkManualMerge` never hold it across foreign I/O: they commit the Flow change, then run the linked-plan sync with no Flow writer held, then persist the `needs_attention` compensation in a second, guarded update. The plan-lock wait uses the Store's own lock budget. That ordering opens a window in which the phase already reads as completed before a failed sync demotes it, and a crash, a lost writer race, or the compensation's stale-state guard can leave no marker at all; recovery for all of them is to repeat the completion, whose plan write is idempotent. The bootstrap/cutover lease has its own longer timeout so a large migration cannot make a second process fail. The root directory is the security boundary for SQLite WAL/SHM sidecars.
- One live `flowstore.Store` at a time per process: it owns a pooled SQLite handle, so the TUI opens it once in `cmd/approach` and hands it to the model through `Options.FlowStore` rather than letting a second pool contend for the same writer. CLI subcommands and session hooks open and `Close` theirs per operation; the hook path opens two sequentially (stale-launch resolution, then attachment) and never holds both. The connection pool is capped well above any realistic fan-out rather than tightly: a writer parked in `BEGIN IMMEDIATE` holds its connection for the whole busy timeout, so a small cap lets writers starve the WAL readers that should never block on them, while no cap at all leaks descriptors permanently — SQLite's unix VFS parks fds it cannot close while the process holds POSIX locks on the inode, so idle-closing a pooled connection does not return its descriptor.
- Branch lists hide non-root worktree branches; the root branch stays pinned at the top.
- Transcripts never live inside repositories — keep them under user state with restrictive permissions (see `docs/agent-sessions.md`).
- The GraphQL API is read-only and never exposes transcripts or session metadata. No `Mutation` or `Subscription` root type exists, the handler rejects non-query operations, and phase `sessions`, `launch_ids`, and transcript paths are absent from the schema by construction.
- When a Flow is linked to a saved plan, transitioning a Flow phase to `completed` syncs a matching saved-plan phase with the same normalized phase ID to `completed`; missing plan phases are ignored, and sync failures mark the Flow phase `needs_attention` — except when the post-commit compensation cannot land, because another writer re-completed that phase in the meantime, because a concurrent writer recorded a merge that the demotion would contradict, or because the compensating update could not acquire the writer, in which case the phase stays completed with a stale plan and the returned error is the only signal. Concurrent writes that leave the completion itself alone, such as attaching a session or recording a resume launch, do not suppress the marker. Repeating `completed` for an already-completed Flow phase preserves that completed state even if the linked-plan sync later fails, and re-runs the idempotent plan write.
- Flow repair launches export the Flow ID and shared artifact root with an empty phase ID, never call `AddPhaseLaunchID`, and cannot attach a captured session to phase history. A runtime Flow/launch-ID reservation fences duplicate and replayed repair messages. Immediately before terminal allocation, `Store.ReserveRepairLaunch` holds an advisory lock shared with `CloseFlow`, reads the authoritative Flow, revalidates eligibility, reapplies the authoritative per-Flow `headless` preference, and releases only after the terminal starts or fails. OS process exit releases a stranded lock automatically.
- Exactly one lifecycle attempt owns a Flow launch at a time, and it never lapses. This covers manual, automatic, and resume launches alike; a tracked phase resume takes the attempt at the key press and holds it across its own read and write. An attempt owns it from admission until the embedded slot is installed (the slot then owns it) or until an external handoff's result is consumed; failure persistence re-takes ownership before the slot is dismissed, so the Flow is never unowned while its phase is persisted `running`. Ownership is keyed on the exact canonical Flow ID, released on a token match only, and entered into `failurePersisting` only after `flowLaunchFailureUpdate` confirms there is something to persist — otherwise no persistence message arrives and the Flow would be reserved forever.

## Behavioral Notes

- Flow auto-advance is view-independent: a private unscoped advance poll detects live completion edges and launches the next AutoMode phase headlessly without changing focus or mode, regardless of the Flow's stored manual-launch preference. A cleanly exited repair slot adds a one-shot marker fenced to the first successful unscoped poll generation that began after exit; the marker can re-arm the same non-merge drain after metadata-only repair or a running-to-ready reset. Retained repairs suppress ordinary completion-edge drains, and non-clean removal records a generation-fenced suppressing outcome that remains until a later state first exposes launchable work, so failure, termination, prefill failure, or a detached agent's delayed mutation cannot leak a deferred launch. The latest repair removal outcome is authoritative, allowing a clean retry to replace an earlier failure. Admission, candidate validation, and retry all belong to the launch lifecycle: the drain picks a candidate and submits an intent, and everything after that is the lifecycle's. The lifecycle also lists the Flow's sessions before an automatic launch and refuses while a session on the candidate phase is still live, re-arming so the launch resumes when it ends — which means a session record that never reaches `ended` stalls that Flow's AutoMode silently: repair sees no obstruction while the phase is still launchable, and reset requires `running`. Manual launch refuses on the same occupancy rule but names it (`flowLaunchPhaseSessionLiveStatus`) and points at the route out, which is `x` on the selected phase. Session release is that route: `handleReleaseSelectedFlowPhaseSession` probes both halves through the launch seams, and a confirmation finalizes each still-live launch through the same `FinalizeAgentSession` a clean exit would have run, so no store API and no persisted shape is new. It refuses phase-wide while any agent is provably live on the phase, and the confirmation states that the sessions are unverified, because outside the embedded backend and tmux nothing can prove they are not. AutoMode itself still says nothing — the drain short-circuits on the phase mirror before the read stage, and `handleAutoFlowLaunchRead` may not set a status — so the affordance is the footer hint and the named manual refusal. Phase resume does not join the occupancy list — its check exempts the session it is reattaching to, so `r` still gets a user back into the work — but it is not a cure either: reattaching does not finalize the stale record, and whether the record clears depends on whether the provider reuses its session ID. Because that refusal re-arms, the drain applies the same check to the mirrored sessions the poll snapshot already carries before it submits an intent; otherwise a stalled phase would re-admit and walk the whole session store once a second for as long as it stayed stalled. A 3 s transient status announces auto-launches, `needs_attention`, and merge-ready transitions unless another status from a different source is active; the auto-launch announcement is emitted once the authoritative read and preflight have passed, so a Flow that is refused before it launches announces nothing. It therefore lands a hop after the transition statuses computed by the same poll, which would invert their precedence; the auto-advance source is ranked to absorb that, so a transition edge outranks both the queued announcement and a launch failure while messages of equal rank still replace each other.
- Launch backend (`[launch].backend`) selects between the embedded terminal (default) and tmux mode. The Flow lifecycle carries it as a third route (`flowLaunchRouteTmux`, chosen in `FlowPhaseLauncher.Prepare` for a phase launch and in `phaseResumeFlowLaunchPrepareCmd` for a phase resume, which builds its own context rather than going through the launcher); the non-lifecycle paths branch through `Model.tmuxLaunchRoute` in `model/tmux_mode.go`. Both wrap the single rule in `tmuxLaunchRouteFor`, because the launcher holds a snapshot of the backend and probe taken at admission while the Model reads config's live values — two holders of the same decision, not two decisions. Tmux-route contexts carry `Embedded = false` — that single bit is what sends `InitialPrompt` to argv instead of an embedded dock prefill that would never arrive. Tmux launches use external handoff semantics throughout: detached result, no embedded slot, hook-owned completion, and no quit-time cleanup. Headless launches, Flow repair, and the plan launch that Flow creation performs never take the tmux route. One consequence is load-bearing: the embedded slot is also the "an agent is live here" fence for phase reset, repeat resume, Flow repair, and phase session release, and a tmux window is not an observable slot. Persisted session state cannot substitute — Claude's hook is `SessionEnd`, so a live window has no session at all, while Codex's `Stop` hook records an `ended` session per turn — so all four actions probe tmux directly (`RepoTmuxLaunchWindowLive`, matching the launch IDs that `repoTmuxWindowName` embeds in window names). The probe is variadic and takes every launch ID the caller owns, because one `list-windows` answers for all of them and an earlier launch's window can outlive a later one that already exited: reset, resume, and release pass the phase's launches, repair passes the whole Flow's, since a repair agent is Flow-wide and a Flow-level obstruction names no phase. Release passing all of them is also what makes its refusal phase-wide, which is the point: a phase can carry a resumed live launch beside a crashed one, and finalizing "every live launch" would record the working agent as ended. Two invariants: the probe belongs only on the one-shot user-initiated choke points (`handleFlowPhaseResetConfirmed`, `handleResumeFlowPhaseSession`, `handleRepairSelectedFlow`, `handleFlowPhaseSessionReleaseConfirmed`) and never in a render-path predicate like `flowPhaseResettable`, `selectedFlowRepairReady`, or `flowPhaseSessionReleasable`, and it is advisory in one direction only — a failed probe reports "no live window" so it can never strand a phase. Do not replace it with a fence keyed on a recorded launch ID: with no release condition, an out-of-band `tmux kill-window` would make the phase permanently unresettable. Because the tmux transport spawns through a wrapper script, its failures would otherwise reduce to the script's exit status; `TerminalLaunchSpec.ErrorDetail` carries the captured stderr into the launch error a Flow persists as its `needs_attention` note.
- Embedded terminals (sessions-mode resumes and flows-mode CLI launches) are runtime-only and not persisted or restored; quitting while any are running asks for confirmation before terminating them. Keep PTY mechanics in `embeddedterm`; model owns one global slot selection and dock state, unified `ctrl+]` command routing, picker/confirm state, session/Flow lifecycle metadata, and conversion from saved sessions to `actions.AgentCommand` contexts. `codex-app` session resumes and flow launches continue to use the external deep-link path.
- Keep ordinary Flow phase launch prompts minimal: state the action plus essential location metadata (worktree, branch, commit). Don't embed plan bodies, phase history, or status-update recipes unless the phase can't work without them. Repair prompts are the deliberate exception: they include the obstruction and structured recovery safety rules because the session is untracked and must leave persisted state honest.
